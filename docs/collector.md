# Передача ПО исполнителям и приём датасета

Цикл, ради которого сделано (решение владельца 28.08.2026): найти
исполнителей → отдать им программу → они играют → присылают данные,
когда захотят → данные попадают в датасет фазы 6. Всё, что здесь
описано, живёт в `src/app/`, `src/collector/`, `src/dataset/import.ts`
и закреплено тестами; что проверить не удалось — сказано отдельно.

```
npm run collector                       трей: сборщик логов (+ оверлей по галочке)
npm run overlay                         то же с включённым оверлеем
npm run collect                         сборщик в терминале, без Electron
npm run collect -- --export             собрать архив для отправки и выйти
npm run dataset:import -- <файл.tar> [--from <псевдоним>] [--rating <число>]
npm run dataset:import -- <файл.tar> --own      свои партии с установленного приложения
npm run dist                            инсталлятор → release/
npm run dist:dir                        распакованная сборка → release/win-unpacked/
```

## Главное решение: передаются сырые логи, а не записи датасета

Записи датасета (`data/dataset/*.json`) — производная от редьюсера
ТОЙ версии приложения, которая стояла у игрока. Редьюсер меняется
еженедельно: `lobby` вошёл в состояние 18.08, `actions` — 19.08 (и их
пришлось досыпать из фикстур), `heroPowerScriptData` — 28.08. Запись
старой сборки не обновить; лог перечитывается любой будущей версией —
ровно это делает `dataset:backfill`. Дальше арифметика:

| | записи датасета | сырой Power.log |
|---|---|---|
| размер на партию | ~450 КБ | 28.8 МБ → **1.44 МБ** gzip (part33, ×20) |
| зависит от версии приложения | да | нет |
| зависит от свежести снапшота карт | нет | нет |
| годится в фикстуру | нет | как есть |
| проверяется на приёме | по полям | разбором: CREATE_GAME → FINAL_GAMEOVER |

Парсер от языка клиента не зависит: в `src/parser` и `src/state` нет
сопоставлений по локализованным строкам («Бармен Боб» — только
в комментариях). Исполнитель с английским клиентом ничего не ломает.

Записи датасета по-прежнему пишутся живым режимом на СВОЕЙ машине
(оверлей) и генерируются из чужих логов командой импорта.

## Пути: из репозитория и из сборки (`src/app/paths.ts`)

До этого все пути были строками от рабочего каталога. У исполнителя
с инсталлятором рабочий каталог произвольный, а Program Files
не пишется: первый же `mkdirSync` рекордера датасета упал бы внутри
обновления состояния — молча, потому что у GUI-сборки Electron нет
стандартного вывода (docs/live.md).

| | из репозитория | из сборки |
|---|---|---|
| `dataDir` (карты, статистика) | `<repo>/data` | `<exe>/resources/data` (extraResources) |
| `homeDir` (датасет, архив, настройки) | `<repo>/data` | `%LOCALAPPDATA%\hs-bg-assistant` |

Признак сборки — снапшот карт в `process.resourcesPath`, а не
`app.isPackaged`: пути нужны и CLI, и воркеру, и тестам. Под Electron
без сборки `resourcesPath` указывает в `node_modules` — данных там нет,
и это честно «репозиторий». `HSBG_DATA_DIR` и `HSBG_HOME` перекрывают
любое правило. Корень репозитория берётся от собственного модуля
(`src/app` и `dist/app` на одной глубине), не от `process.cwd()`.

## Где установлена игра (`src/watcher/installDir.ts`)

Проверено на машине разработки 28.08: инсталлятор Blizzard регистрирует
игру в обычной ветке удаления программ —

```
HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\Hearthstone
  InstallLocation    REG_SZ    C:\Program Files (x86)\Hearthstone
```

Веток `Blizzard Entertainment` в HKLM/HKCU на той же машине нет;
`Battle.net.config` в `%APPDATA%` содержит путь к самому Battle.net,
не к игре. Порядок: явный путь из настроек → реестр (каталог обязан
содержать `Hearthstone.exe`) → перебор типичных каталогов по всем
дискам → прежняя константа (чтобы сообщение «логов не нашлось в …»
называло конкретный путь). В трее есть «Указать папку Hearthstone…».

## Сборщик (`src/collector/archive.ts`)

Hearthstone заводит папку логов на каждый запуск клиента и в старую
больше не пишет. Отсюда две ветви:

- **завершённые сессии** (все, кроме самой свежей) сжимаются с диска —
  досбор подбирает и партии, сыгранные без нашего приложения, лишь бы
  конфиги логирования были в порядке;
- **свежая сессия** копируется живьём в `.part` тем же `FileTailer`,
  что и советник: если клиент начнёт чистить старые папки, копия
  останется. При смене сессии копия сжимается, а досбор дожимает её
  с источника уже как завершённую (источник полнее копии на всё, что
  игра дописала после нашей остановки).

Файлы в `games/`: `<сессия>.Power.log.gz`, `<сессия>.meta.json`
(байт источника, завершена ли, шёл ли оверлей, версия приложения),
живая `<сессия>.Power.log.part`. Сирота `.part` без источника (упали,
не дожав; клиент почистил папку) сжимается как есть. Сжатие потоком:
сессия из пяти партий — полторы сотни мегабайт.

**Флаг оверлея в метаданных — не украшение.** Партия, сыгранная
по подсказкам, для датасета «как играют люди» — другой класс данных
(второй контур петли, docs/ml.md). У исполнителя оверлей выключен
по умолчанию; включённый пишется в каждую сессию и доезжает до записи
датасета полем `overlay`.

## Экспорт (`src/collector/export.ts`, `tar.ts`)

Один файл: `hsbg-logs_<дата>.tar` на рабочем столе — `manifest.json`
(формат `hsbg-logs/1`, версия приложения, список сессий) плюс `.gz`
и `.meta.json` каждой сессии. Перед сборкой живая сессия снимается:
игрок нажимает «собрать» обычно сразу после игры. Повторный экспорт
присылает ту же сессию полнее — приём различает партии по отпечатку,
а не по файлу.

Контейнер — ustar своими руками (без зависимостей; ни zip, ни tar
в Node нет): 512-байтные заголовки, восьмеричные поля, prefix/name
для длинных имён. Тест проверяет, что штатный `tar.exe` Windows 11
(bsdtar) видит те же файлы: контейнер, который открывается только
нашей командой, был бы плохим форматом для передачи. Сжатия
у контейнера нет: содержимое уже сжато.

Никакой сети: файл отправляется любым файлообменником. Загрузка
на сервер — если понадобится — только явной кнопкой, как
`update:cards`.

## Приём (`src/dataset/import.ts`)

`npm run dataset:import -- hsbg-logs_….tar [--from alias] [--rating N]`:

1. контейнер читается, манифест проверяется (чужой файл — ошибка,
   не тихий ноль);
2. каждая сессия режется на партии по строке `CREATE_GAME`
   канала-источника (`GameState.DebugPrintPower`; дубль из
   `PowerTaskList` партию не начинает — в part33 два CREATE_GAME
   при четырёх FINAL_GAMEOVER, потому что лог сессии — это несколько
   партий и переподключений);
3. каждая партия прогоняется ТЕМ ЖЕ пакетным путём, что досбор
   (`reduceLog` + `readTavernTurns`), — эквивалентность живому пути
   закрыта тестами `feed.test.ts`;
4. принимается партия с `FINAL_GAMEOVER` и местом, хотя бы одной
   точкой решения и НОВЫМ отпечатком (`gameSignature` — тот же,
   что у досбора; витрина первого хода случайна, между людьми
   совпадений нет);
5. запись ложится в общий каталог датасета с префиксом
   `c-<псевдоним>_<сессия>_g<номер>_b<билд>_p<место>.json` и полями
   `contributor`, `contributorRating` (со слов — в логе рейтинга нет,
   проверено grep по part33), `overlay`; загрузчик фазы 6 читает
   каталог плоско и ничего о них знать не обязан;
6. сырой архив раскладывается в `contrib/<псевдоним>/<имя архива>/`
   как пришёл — партия исполнителя, где советник ошибся, становится
   `partN` без преобразований.

Отчёт печатает принятое и пропущенное С ПРИЧИНОЙ — исполнителю
платят за партии, и счёт обязан быть объясним: **не Battlegrounds**
(строка `GameType=` канала DebugPrintGame после CREATE_GAME:
у Battlegrounds `GT_BATTLEGROUNDS`, первый же архив игрока принёс
сессию из четырёх партий `GT_RANKED` — Standard, — и без проверки они
шли «обрывом на ходу 22», то есть как вина исполнителя), **обрыв**
(лог кончился до FINAL_GAMEOVER — клиент закрыт посреди партии либо
не снят предел 10 000 КБ), **нет точек решения**, **дубль**,
**не разобран**. Сегмент переподключения (первая точка не на первом
ходу) принимается с пометкой `partial`, как его пишет и живой рекордер.

**Свои партии через ту же трубу: `--own`.** Установленное приложение
пишет записи датасета в `%LOCALAPPDATA%`, а в режиме сборщика (оверлей
выключен) не пишет их вовсе, — значит, собственные партии владельца
теперь попадают в датасет репозитория тем же архивом:
`npm run dataset:import -- <tar> --own`. Записи ложатся без поля
`contributor` (отсутствие и значит «своя»), с префиксом `own_`,
сырой архив — в `contrib/own/`.

Псевдоним без `--from` — BattleTag из лога (`AngryMem#2886` →
`AngryMem-2886`): он есть в каждом логе, и по нему же парсер
отличает «кто я». Анонимизировать логи нельзя — имя используется
атрибуцией TAG_CHANGE (`players.ts`); это персональные данные
исполнителя и имена его соперников, и об этом сказано в памятке
(docs/contributor.md).

## Годна ли запись импорта так же, как запись оверлея — ЗАМЕРЕНО 29.08

Вопрос игрока после первого цикла. Материал — его же партии, записанные
обоими путями. Скрипт сравнения — разовый (scratchpad), выводы здесь.

**A. Хранимые записи оверлея (27–28.08) против импорта тех же логов:**
четыре пары, точки те же (11/11, 9/9, 3/3; у part34 — 17 против 16),
журнал действий тождественен во всех, а состояния расходятся во всех
точках — и все расхождения от ВЕРСИИ редьюсера на момент записи:
`buyCost` у каждого миньона (part35, вечер 28.08) даёт сотни расхождений
в `board`/`shop`/`lastSeenBoards`, `heroPowerScriptData` — в `hero`,
`TEMP_RESOURCES` — в `gold` и в числе точек part34. Это ровно то,
о чём говорит «запись — снимок старой схемы»: старые записи оверлея
дополняет загрузчик, а импорт даёт запись текущей схемы.

**B. Один лог, оба пути, один редьюсер** (живой — порции 4 КБ и 64 КБ
→ `LineAssembler` → `GameFeed` → `DatasetRecorder`; пакетный —
`reduceLog` + `readTavernTurns`, как в импорте), две партии:

| | точек | ходы | действия | тождественных точек | что расходится |
|---|---|---|---|---|---|
| 17:18, 4 КБ | 9/9 | те же | 260 = 260 | 1 из 9 | `tags.1196`×28, `lobby`×10, `EXHAUSTED`/`NUM_TURNS_IN_PLAY`/`CANT_ATTACK`×2, `BACON_PAIR_CANDIDATE`×1 |
| 17:18, 64 КБ | 9/9 | те же | 260 = 260 | 5 из 9 | `lobby`×9, `tags.1196`×6, те же служебные |
| 12:16, 4 КБ | 10/10 | те же | 151 = 151 | 4 из 10 | `tags.1196`×16, `lobby`×5, `openChoice`×2, `trinketsByPlayer`×2 |
| 12:16, 64 КБ | 10/10 | те же | 151 = 151 | 6 из 10 | `lobby`×3, `openChoice`×2, `trinketsByPlayer`×2 |

Причина одна и структурная: оба пути берут «последнее состояние
до первой траты», но пакетный снимает его на последнем событии
с `ZONE`/`RESOURCES`/`BOARD_VISUAL_STATE` (фильтр `readTavernTurns` —
снимок дорог), а живой — на конце порции, то есть на несколько
событий ПОЗЖЕ: тег `1196` (безымянный, мигает 0/1 на миньонах),
`EXHAUSTED`, тир соперника в `lobby`, закрытый выбор тринкета.
**И не только служебное:** тест на part7 нашёл точку (одну из девяти),
где атака миньона борда в пакетной записи 44, в живой 48 — усиление
пришло тегом `ATK` без ZONE/RESOURCES после последнего пакетного
снимка. Что совпадает во всех точках и закреплено тестом
(`test/dataset/import.test.ts`, «то же, что записал бы живой путь»):
ходы, золото, тир, hp, СОСТАВ борда, рука, витрина, место, число живых,
журнал действий; сумма статов борда расходится не больше чем в одной
точке партии.

Порция в 1 МБ (догон файла целиком) теряет точки (7 из 9, 6 из 10) —
известное свойство живого пути: помощник, запущенный посреди партии,
пишет ходы после запуска. Импорту это не грозит — он читает с начала.

Вывод: запись импорта того же класса, что 23 партии из фикстур
и 28 пересобранных 28.08 записей, — то есть ОСНОВНОЙ массы датасета,
которая вся идёт пакетным путём; «нетипичны» как раз записи оверлея.

### Правка 29.08 по решению игрока: пакетный снимок — перед действием

`readTavernTurns` теперь снимает состояние ПЕРЕД действием, которое
тратит золото, а не на последнем ZONE/RESOURCES-событии. Первый заход —
«перед событием `RESOURCES_USED`» — уронил тест part11 (ход 5, сила
героя): трата приходит ВНУТРИ блока `PLAY`, и первые строки блока уже
меняют состояние (флаг «сила нажата» на BLOCK_START, золото строкой
позже — part30), так что снимок попадал внутрь действия. Граница —
начало верхнего блока: строки BLOCK_START событиями не являются,
первое событие блока несёт весь открытый стек с тем же объектом
верхнего блока до конца блока, и состояние снимается перед первым
событием каждого нового верхнего блока; трата вне блоков (тринкет
за золото, part32) — перед самим событием. Лишних снимков — по одному
на верхний блок хода до первой траты.

Перезамер тем же скриптом (те же две партии, порции 4 КБ и 64 КБ):

| | тождественных точек | что осталось |
|---|---|---|
| 17:18, 4 КБ | 2 из 9 | `tags.1196`×21 |
| 17:18, 64 КБ | 2 из 9 | `tags.1196`×43, `lobby`×1 |
| 12:16, 4 КБ | 3 из 10 | `tags.1196`×47 |
| 12:16, 64 КБ | 2 из 10 | `tags.1196`×63, `lobby`×4 |

Статы борда, `EXHAUSTED`, `NUM_TURNS_IN_PLAY`, `CANT_ATTACK`,
`BACON_PAIR_CANDIDATE`, `openChoice`, `trinketsByPlayer` — сошлись все.
Остался безымянный тег `1196`, мигающий 0/1 на миньонах внутри самого
действия (живая порция ловит его посреди блока, пакетный снимок стоит
перед блоком), и единичные обновления тира соперников в `lobby`
на крупных порциях. Ни то ни другое в признаки не входит. Тест
эквивалентности (`test/dataset/import.test.ts`) держит равенство
своего положения, включая статы борда.

Полный прогон после правки: упал ровно один тест из 853 (part11,
описан выше), после переноса границы на начало блока — все зелёные;
ни одно ожидание тестов советника переписывать не пришлось. Датасет
пересобран `dataset:backfill --rebuild` (флаг добавлен ради этого:
`refreshRecord(…, force)` пересобирает и запись текущей схемы —
точки сдвинулись по определению, а не по схеме): 28 записей
(23 партии part4–part26, part17–21 двойные, как и были), число точек
у всех прежнее, **новых записей 0 — отпечаток первой точки
(`gameSignature`) не сдвинулся ни у одной**, дедуп загрузчика сводит
всё как раньше (ожидаемо: состав витрины меняют только ZONE-события,
а они снимались и прежде). Десять живых записей 26–28.08 (part27–35
не в `CURRENT_BUILD_PARTS`) не тронуты — они живого пути; своя запись
с установленного приложения пересобрана повторным `dataset:import
--own`. Резервная копия датасета до пересборки — в scratchpad сессии.

## Приложение в трее (`src/app/main.ts`) и упаковка

Трей: версия, сколько сессий в архиве и за какой следим, галочка
«Оверлей с советами» (сохраняется в `config.json`), «Собрать архив
для отправки…», «Открыть папку с данными», «Указать папку
Hearthstone…», «Выход». `Ctrl+Shift+Q` теперь выключает ОВЕРЛЕЙ,
а не приложение — сборщик в трее продолжает работать. Второй
экземпляр не запускается (`requestSingleInstanceLock`). Оверлей
вынесен в `src/overlay/window.ts` функцией `startOverlay` — тот же
код окна, что был в `overlay/main.ts`, без жизненного цикла приложения.

Настройки игры: `log.config` правится без прав; `client.config`
в каталоге игры — в сборке приложение перезапускает себя через UAC
с ключом `--setup` (`src/app/elevate.ts`, PowerShell
`Start-Process -Verb RunAs -Wait -PassThru`, кавычки проверены
тестом), а инсталлятор делает то же сразу после копирования файлов
(`build/installer.nsh`, макрос `customInstall`), так что UAC при
запуске — запасной путь. Без этого лог обрывается на 10 МБ, партия
не долетает до конца и на приёме отбраковывается — деньги за неё уже
уплачены.

Упаковка — `electron-builder.yml`: NSIS с правами на машину, asar
выключен (воркер грузится по пути к файлу), снапшот карт и статистика —
`extraResources`, иконка — сгенерированная монета (`src/app/icons/`).

## Что проверено, а что нет

Проверено тестами: пути (из репозитория / из сборки / переменные),
разбор реестра на дословном выводе `reg query`, контейнер (включая
чтение bsdtar), архиватор на настоящих файлах (досбор, живая сессия,
смена сессии, сирота, обрезка источника, экспорт), импорт на part7
(приём, дубль, обрыв, чужой файл), настройки, команда повышения прав.

Проверено настоящим циклом на логах машины разработки 28.08:
`npm run collect -- --export` (с `HSBG_HOME` во временный каталог)
сжал пять сессий клиента — 203 МБ источника — в `hsbg-logs_….tar`
на 10.2 МБ за 2.5 с; `npm run dataset:import` принял из него три партии
(part33 — 5-е место, 11 точек; part34 — 1-е, 16 точек; ещё одна —
3-е, 9 точек) под псевдонимом из BattleTag и назвал два обрыва: сессия
без партии («лог кончился на ходу 0») и партия, оборванная
переподключением на ходу 19, — за 32 с. Цикл нашёл два дефекта, которых
тесты не видели: досбор без `start()` падал на отсутствующем каталоге,
а экспорт из терминала не включал свежую сессию (снимок живой копии
делает только опрос). Оба закрыты, первый — тестом.

Сборка `electron-builder --dir`: собирается, `resources/data` на месте,
пути внутри сборки разрешаются в `resources/data` и
`%LOCALAPPDATA%\hs-bg-assistant` (проверено запуском собранного
`paths.js` под `ELECTRON_RUN_AS_NODE`). Распакованная сборка — 420 МБ,
из них 216 МБ сам Electron.

Инсталлятор (`npm run dist`, 29.08): собрался — `release/HS BG Assistant
Setup 0.1.0.exe`, 107 МБ; NSIS скачан electron-builder-ом, скрипт
с нашим хуком скомпилирован (`build/installer.nsh` включён в сборку,
`${APP_EXECUTABLE_FILENAME}` существует — при неизвестной переменной
makensis падает). Собранное приложение в режиме `--setup` выходит
с кодом 0 за секунду: ESM-вход, пути и проверка конфигов внутри сборки
работают.

**Не проверено глазами** — по той же причине, что и оверлей
(docs/live.md): в среде разработки нет интерактивного рабочего стола.
Сама установка, запрос UAC, трей, диалоги и работа хука `--setup`
из-под инсталлятора проверяются только у игрока.

## Что сознательно не сделано

- **Сервер и автозагрузка.** Файлообменника хватает; сеть в рантайме —
  против правил проекта. Явная кнопка «отправить» — следующий шаг, если
  пересылка файлов руками начнёт мешать.
- **Автообновление.** Новый патч игры требует нового снапшота карт только
  оверлею; сборщику логов патч безразличен. Сборка обновляется вручную.
- **Рейтинг в записи — со слов.** В Power.log его нет. Альтернатива —
  скриншот от исполнителя при каждом пакете; в договоре это условие.
- **Партии старого патча.** Датасет учит только новейший патч
  (`src/data/builds.ts`): партии исполнителей, сыгранные до контентного
  патча, для ML пропадают, для тестов парсера остаются. Пакеты стоит
  принимать чаще, чем выходят патчи.
- **`ml:track` не считает по исполнителям.** Поле `contributor` в записи
  есть; счёт по людям и фильтр «без оверлея» — вместе с перезамером,
  когда партий станет больше.
