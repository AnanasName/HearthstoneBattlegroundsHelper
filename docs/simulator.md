# Симулятор боя: контракт и что он требует от парсера

Результаты спайка `npm run spike:battle` от 04.08.2026.
Пакет `@firestone-hs/simulate-bgs-battle@1.1.726`, MIT, одна зависимость
`@firestone-hs/reference-data`.

## Главное

Симулятор **заводится и работает быстрее, чем требует ТЗ**. Риск, который
я закладывал в начале проекта — что интеграция окажется работой на недели, —
не подтвердился: публичный API оказался узким и документированным типами.

## API

```ts
simulateBattle(
  battleInput: BgsBattleInfo,
  cards: AllCardsService,
  cardsData: CardsData,
): Generator<SimulationResult, SimulationResult, void>
```

Генератор нужно прокрутить до `done`, последнее значение — итог.

## Данные карт — без сети

`AllCardsService.initializeCardsDbFromCards(cards)` принимает готовый массив,
сеть не нужна. Снапшот лежит в `data/cards/cards_enUS.json`:

- источник: `https://static.zerotoheroes.com/data/cards/cards_enUS.gz.json`
- 38.7 МБ на диске, около 3.3 МБ в git
- 35 321 карта, из них 1833 миньона BG (есть `techLevel`) и 1032 золотых

⚠️ **`cards.collectible.json` из ТЗ не годится.** Нужен полный набор Firestone:
он содержит поля `techLevel`, `isBaconPool`, `races`, которых в коллекционном
срезе HearthstoneJSON нет, а симулятор на них опирается.

Побочно снапшот подтвердил две вещи, которые до того были наблюдениями:
`BG27_Anomaly_301` — это действительно **False Idols**, а золотые миньоны
существуют **отдельными картами** с суффиксом `_G`.

## Производительность

Замеры на борде 7 на 7, то есть в худшем случае по размеру.

| симуляций | время |
|---:|---:|
| 300 | 47 мс |
| 1000 | 93 мс |
| 3000 | 249 мс |

**Фаза 2 укладывается с девятикратным запасом**: ТЗ отводит 2000 мс на 3000
симуляций, фактически выходит около 250.

**Фаза 3 выполнима, вопреки моей ранней оценке.** Я предполагал, что полный
перебор займёт около 17 минут, и считал это самой недооценённой частью ТЗ.
Ошибка была в том, что я взял бюджет из ТЗ (2 с на 3000 симуляций) за факт
производительности, тогда как симулятор быстрее почти на порядок:

| стратегия | время |
|---|---:|
| полный перебор 5040 × 300, один поток | ~125 с |
| он же на 8 воркерах | ~16 с |
| beam search 200 кандидатов × 300 | ~5 с |

То есть beam search укладывается в разумный бюджет даже без воркеров, а с ними
запас становится комфортным. Полный перебор остаётся пригоден как эталон
для офлайн-проверки качества поиска.

Отдельно про шум: при 300 симуляциях стандартная ошибка доли около 3%, а разница
между хорошей и отличной расстановкой часто 1–3%. Выбор максимума из тысяч
зашумлённых оценок даст не лучшую расстановку, а самую удачливую. Нужны общие
случайные числа для всех кандидатов и перепрогон финалистов увеличенным N —
это надо закладывать в дизайн фазы 3, а не чинить потом.

## Что симулятор хочет на входе

### `BgsBattleInfo`

```ts
{
  playerBoard: BgsBoardInfo;
  opponentBoard: BgsBoardInfo;
  options: { numberOfSimulations: number; skipInfoLogs: boolean; … };
  gameState: { currentTurn: number; validTribes?: Race[]; anomalies?: string[] };
}
```

### `BoardEntity` — один миньон

Обязательны `entityId`, `cardId`, `attack`, `health`. Всё остальное опционально,
но влияет на точность.

| поле | статус в нашем `GameState` |
|---|---|
| `entityId`, `cardId`, `attack`, `health` | ✅ есть |
| `taunt`, `divineShield`, `poisonous`, `venomous`, `reborn`, `windfury` | ✅ есть |
| `tavernTier` | ✅ есть как `techLevel` |
| `cleave` | ❌ нет |
| `stealth` | ❌ нет |
| `enchantments: BoardEnchantment[]` | ❌ нет |
| `scriptDataNum1…6` | ❌ нет, в логе это `TAG_SCRIPT_DATA_NUM_1…6` |
| `tags: { [tag: number]: number }` | ❌ нет |
| `maxHealth`, `maxAttack` | ❌ нет |
| `avengeCurrent`, `avengeDefault` | ❌ нет |
| `frenzyChargesLeft` | ❌ нет |

`BoardEnchantment` — это `{ cardId, timing, tagScriptDataNum1?, tagScriptDataNum2?, … }`.
То есть симулятору нужны энчанты **списком с их cardId**, а не только итоговые
статы миньона. Это ровно тот вопрос, который висел в пробелах документации,
и ответ на него: **итоговых статов недостаточно**.

### `BgsPlayerEntity` — герой

Обязательны `cardId`, `hpLeft`, `tavernTier`, `heroPowers`, `questEntities`.

| поле | статус |
|---|---|
| `cardId`, `hpLeft`, `tavernTier` | ✅ есть |
| `heroPowers: BgsHeroPower[]` | ❌ нет |
| `questEntities`, `questRewards` | ❌ нет |
| `trinkets: BoardTrinket[]` | ❌ нет, хотя в фикстуре part1 тринкеты есть |
| `hand: BoardEntity[]` | ⚠️ рука есть, но без полей BoardEntity |
| `globalInfo` | ❌ нет, около 60 счётчиков |

`BgsPlayerGlobalInfo` — набор накопительных счётчиков вроде
`BloodGemAttackBonus`, `PiratesPlayedThisGame`, `UndeadAttackBonus`,
`BeetleAttackBuff`. Они меняют исход боя напрямую, и без них симуляция будет
систематически ошибаться на бордах, завязанных на эти механики.

## План работ, вытекающий из спайка

Порядок по важности для точности:

1. **Энчанты миньонов** — списком, с `cardId` и `timing`. Без них не считаются
   бафы, а значит и исход.
2. **`globalInfo`** — счётчики игрока. Большой, но механический объём;
   источники в логе есть, это `BACON_*` теги.
3. **Сырые `tags` и `scriptDataNum1…6`** — дёшево, они уже проходят через
   редьюсер, надо перестать их отбрасывать.
4. **`cleave`, `stealth`, `maxHealth`, `maxAttack`** — мелочь.
5. **Тринкеты и силы героя** — отдельные сущности, в логе видны.
6. **`validTribes`** — племена в партии, в логе `BACON_SUBSET_*`.

Пункты 1–3 стоит сделать до первых замеров точности: без них сравнение
предсказаний с фактическими исходами боёв будет мерить не симулятор,
а полноту нашего маппинга.
