# Симулятор боя: контракт и что он требует от парсера

Результаты спайка `npm run spike:battle` от 04.08.2026.
Пакет `@firestone-hs/simulate-bgs-battle@1.1.726`, MIT, одна зависимость
`@firestone-hs/reference-data`.

## Главное

Симулятор **заводится и работает быстрее, чем требует ТЗ**. Риск, который
я закладывал в начале проекта — что интеграция окажется работой на недели, —
не подтвердился: публичный API оказался узким и документированным типами.

## API

```ts
simulateBattle(
  battleInput: BgsBattleInfo,
  cards: AllCardsService,
  cardsData: CardsData,
): Generator<SimulationResult, SimulationResult, void>
```

Генератор нужно прокрутить до `done`, последнее значение — итог.

## Данные карт — без сети

`AllCardsService.initializeCardsDbFromCards(cards)` принимает готовый массив,
сеть не нужна. Снапшот лежит в `data/cards/cards_enUS.json`:

- источник: `https://static.zerotoheroes.com/data/cards/cards_enUS.gz.json`
- 38.7 МБ на диске, около 3.3 МБ в git
- 35 321 карта, из них 1833 миньона BG (есть `techLevel`) и 1032 золотых

⚠️ **`cards.collectible.json` из ТЗ не годится.** Нужен полный набор Firestone:
он содержит поля `techLevel`, `isBaconPool`, `races`, которых в коллекционном
срезе HearthstoneJSON нет, а симулятор на них опирается.

Побочно снапшот подтвердил две вещи, которые до того были наблюдениями:
`BG27_Anomaly_301` — это действительно **False Idols**, а золотые миньоны
существуют **отдельными картами** с суффиксом `_G`.

## Производительность

Замеры на борде 7 на 7, то есть в худшем случае по размеру.

| симуляций | время |
|---:|---:|
| 300 | 47 мс |
| 1000 | 93 мс |
| 3000 | 249 мс |

**Фаза 2 укладывается с девятикратным запасом**: ТЗ отводит 2000 мс на 3000
симуляций, фактически выходит около 250.

**Фаза 3 выполнима, вопреки моей ранней оценке.** Я предполагал, что полный
перебор займёт около 17 минут, и считал это самой недооценённой частью ТЗ.
Ошибка была в том, что я взял бюджет из ТЗ (2 с на 3000 симуляций) за факт
производительности, тогда как симулятор быстрее почти на порядок:

| стратегия | время |
|---|---:|
| полный перебор 5040 × 300, один поток | ~125 с |
| он же на 8 воркерах | ~16 с |
| beam search 200 кандидатов × 300 | ~5 с |

То есть beam search укладывается в разумный бюджет даже без воркеров, а с ними
запас становится комфортным. Полный перебор остаётся пригоден как эталон
для офлайн-проверки качества поиска.

Отдельно про шум: при 300 симуляциях стандартная ошибка доли около 3%, а разница
между хорошей и отличной расстановкой часто 1–3%. Выбор максимума из тысяч
зашумлённых оценок даст не лучшую расстановку, а самую удачливую.

⚠️ **Дальше следовала рекомендация «нужны общие случайные числа», и она не
подтвердилась.** Замер в фазе 3: на близких кандидатах — тех самых, что решают
первое место, — разброс оценки разницы не уменьшается вовсе (0.9×). Два разных
порядка миньонов расходятся по числу случайных бросков с первого же размена,
и дальше потоки независимы при любом зерне. Из этого абзаца в силе осталась
вторая половина: **перепрогон финалистов увеличенным N**, и именно на нём
построен поиск. Числа и устройство — в [docs/position.md](position.md).

Про производительность здесь тоже занижено: замеры выше сделаны без прогрева.
Фактически 120 мкс на симуляцию плюс 8.5 мс постоянных на каждый вызов
симулятора, то есть полный перебор 5040 расстановок — около четырёх минут,
а не двух.

## Что симулятор хочет на входе

### `BgsBattleInfo`

```ts
{
  playerBoard: BgsBoardInfo;
  opponentBoard: BgsBoardInfo;
  options: { numberOfSimulations: number; skipInfoLogs: boolean; … };
  gameState: { currentTurn: number; validTribes?: Race[]; anomalies?: string[] };
}
```

### `BoardEntity` — один миньон

Обязательны `entityId`, `cardId`, `attack`, `health`. Всё остальное опционально,
но влияет на точность.

| поле | статус в нашем `GameState` |
|---|---|
| `entityId`, `cardId`, `attack`, `health` | ✅ есть |
| `taunt`, `divineShield`, `poisonous`, `venomous`, `reborn`, `windfury` | ✅ есть |
| `stealth` | ✅ есть |
| `tavernTier` | ✅ есть как `techLevel` |
| `enchantments: BoardEnchantment[]` | ✅ есть |
| `scriptDataNum1…6` | ✅ есть |
| `tags: { [tag: number]: number }` | ✅ есть |
| `maxHealth` | ✅ есть |
| `cleave` | ⚠️ тега в логе нет вовсе — это свойство карты, симулятор возьмёт его из базы по `cardId` |
| `maxAttack` | ⚠️ отдельного тега нет; `ATK` и так максимум |
| `avengeCurrent`, `avengeDefault` | ❌ нет |
| `frenzyChargesLeft` | ❌ нет |

Отдельно про золотых: признак — **тег `PREMIUM`**, а не суффикс `_G` в `cardId`.
В эталонной партии 25 золотых миньонов суффикса не имеют, обратных случаев ноль.

`BoardEnchantment` — это `{ cardId, timing, tagScriptDataNum1?, tagScriptDataNum2?, … }`.
То есть симулятору нужны энчанты **списком с их cardId**, а не только итоговые
статы миньона. Это ровно тот вопрос, который висел в пробелах документации,
и ответ на него: **итоговых статов недостаточно**.

### `BgsPlayerEntity` — герой

Обязательны `cardId`, `hpLeft`, `tavernTier`, `heroPowers`, `questEntities`.

| поле | статус |
|---|---|
| `cardId`, `hpLeft`, `tavernTier` | ✅ есть |
| `heroPowers: BgsHeroPower[]` | ⚠️ `cardId` и `entityId` силы героя есть; счётчики использования нет |
| `hand: BoardEntity[]` | ✅ передаётся с 17.08 (part21); поля те же, что у борда, но `maxHealth` обязателен |
| `globalInfo` | ⚠️ семь полей из ~60, см. ниже |
| `questEntities`, `questRewards` | ❌ нет |
| `trinkets: BoardTrinket[]` | ✅ передаются с 14.08: dbfId с героев → cardId справочником |

**Про руку.** Она нужна не для полноты, а потому, что часть карт пула играет
рукой ПРЯМО В БОЮ: «Rally: Summon the highest-Attack minion from your hand for
this combat only» (Expert Aviator), «Whenever this takes damage, give a minion
in your hand +2/+1» (Very Hungry Winterfinner). Симулятор это умеет
(`cards/impl/minion/expert-aviator.js` читает `attackingHero.hand`), и пока
руку не передавали, ралли-призыв считался нулём — строка «по бою» оценивала
носителя ралли как голое тело (part21, ход 5: 77.4% вместо 97.0%).

Тонкость входа: кандидатов на призыв симулятор отбирает условием
`!!e.maxHealth` (`services/hand-minion-priority.js`), а у нас это поле
приходит тегом и в руке бывает пустым — поэтому миньонам руки оно
проставляется от текущего здоровья. Поле `playerHand` в `BattleSetup`
необязательное: у старых эпизодов руки нет, и отсутствие честнее пустого
списка — оно означает «не знаем», а не «рука пуста».

**Про `globalInfo`.** Замаплены только те счётчики, для которых в фикстурах нашёлся
именованный тег: потраченное золото, сыгранные заклинания, карты за ход, бафы
элементалей и заклинаний таверны. Остальные приходят **безымянными числовыми
тегами** — на сущности игрока их 62 штуки за партию, сопоставить их с полями
симулятора не по чему. Плюс набор именованных тегов зависит от механик партии:
счётчики кровавых самоцветов появятся только там, где были кабаны.

**Второй способ, которым игра сообщает счётчик: СУЩНОСТЬ-ЭНЧАНТ** (part50,
07.09.2026). Часть накопительных чисел лежит не на игроке, а на отдельной
сущности под его контроллером, в теге `TAG_SCRIPT_DATA_NUM_1`:

| сущность | что копит | поле симулятора |
|---|---|---|
| `BG25_011pe` «Undead Bonus Attack Player Enchant» | надбавку к атаке ВСЕЙ нежити | `UndeadAttackBonus` |
| `BG25_008pe` «Eternal Knight Player Enchant» | сколько своих Eternal Knight умерло | `EternalKnightsDeadThisGame` |
| `BG26_159pe` «Blood Gem Player Enchant» | размер самоцвета | (читается тегами игрока, part48) |

Читает их `playerEnchantCounters()` в редьюсере — сканом таблицы сущностей
по контроллеру, как кнопка подъёма. **Фильтр по контроллеру несущий:** такой
же энчант есть у каждого из восьми игроков, и в part50 у соперника стоит 36
против наших 284. Без фильтра ошибка была бы не «нет данных», а «чужие данные».

**Почему это важнее, чем выглядит.** На борде статы уже применены игрой,
поэтому без этих полей бой считался бы верно — если бы не ПРИЗЫВЫ. Симулятор
применяет `UndeadAttackBonus` к каждому телу, призванному ВНУТРИ боя
(`dist/simulation/add-minion-to-board.js`, строка 247), а
`EternalKnightsDeadThisGame` — к статам призванного рыцаря (там же, 368).
То есть недооценивалась ровно та композиция, которая на призывах и стоит:
скелеты Cadaver Caretaker, Рука Handless Forsaken, копии перерождения.
Замер — в docs/quality.md, «Надбавка к атаке нежити».

**Про тринкеты.** В зоне `PLAY` лежат только слоты `BG30_Trinket_1st` и
`BG30_Trinket_2nd`, а сами предметы (`BG30_MagicItem_*`, `BG35_MagicItem_*`)
оказываются в `REMOVEDFROMGAME` — и взятые, и отвергнутые при выборе.
Как отличить одно от другого, пока неясно; гадать не стали.

**Про `validTribes`.** Теги `BACON_SUBSET_*` висят на самих миньонах, а не на
`GameEntity`, то есть означают принадлежность карты к племени, а не список племён
партии. За эталонную партию их семь разных, что больше обычного числа активных
племён — значит вывести список прямым объединением нельзя.

`BgsPlayerGlobalInfo` — набор накопительных счётчиков вроде
`BloodGemAttackBonus`, `PiratesPlayedThisGame`, `UndeadAttackBonus`,
`BeetleAttackBuff`. Они меняют исход боя напрямую, и без них симуляция будет
систематически ошибаться на бордах, завязанных на эти механики.

## Калибровка: симулятор проверен фактическими исходами

`npm run calibrate` прогоняет все бои обеих полных фикстур и сравнивает
предсказание с тем, что случилось на самом деле. Исход берётся из лога:
`BACON_WON_LAST_COMBAT` и потеря здоровья согласуются на всех боях.

Результат на **18 боях**:

| метрика | значение |
|---|---|
| фактическая доля побед | 27.8% |
| средняя предсказанная вероятность победы | 31.7% |
| расхождение калибровки | **3.9 п.п.** |
| Brier score | **0.019** (у предсказателя «всегда 50%» было бы 0.25) |
| исходов с вероятностью ниже 5% | 1 из 18 |

Это и есть DoD фазы 2 из ТЗ, переведённый в измеримую форму: формулировка
«фактический исход не является выбросом» по одному бою неопровержима,
а на восемнадцати уже можно считать калибровку.

### Неизвестные счётчики лучше НЕ подставлять нулями

Первый прогон показал в логе симулятора статы `NaN` у спавнов
(`Ancestral Automaton`) и зацикливание — «short-circuiting simulation,
too many iterations». Похоже на отсутствующий счётчик `globalInfo`,
поэтому я попробовал отдавать неизвестные поля нулями. Замеры это опровергли:

| что передаём в `globalInfo` | расхождение | Brier |
|---|---:|---:|
| ничего | 4.0 п.п. | 0.019 |
| нули для неизвестных | 9.1 п.п. | 0.066 |
| **только реально прочитанные** | **3.9 п.п.** | **0.019** |

Выдуманный ноль хуже отсутствия: механика начинает работать с заведомо
неверным значением, тогда как при отсутствии симулятор обходится своими
умолчаниями. Поэтому в `globalInfo` уходят только те семь счётчиков,
для которых в логе есть именованный тег.

`NaN` у спавнов при этом остаётся — это известная незакрытая проблема,
и на неё приходится единственный выброс калибровки (part3, ход 14).

**Один источник `NaN` найден 17.09 — жуки (D239).** `runed-progenitor.js`
и `ravaging-scorpid.js` делают `globalInfo.BeetleAttackBuff += N`; без
поля это `undefined + N`, и `beetle.js` отдаёт `NaN` каждому жуку,
призванному после срабатывания. Поле теперь уходит из счётчика
`BG31_808pe`, когда он есть. Там же ограничение пакета, которое своим
входом не исправить: Scorpid растит жуков на +3, а игра — на +5
(`TAG_SCRIPT_DATA_NUM_3/4` на `BG36_209`).

## План работ, вытекающий из спайка

Порядок по важности для точности:

1. **Энчанты миньонов** — списком, с `cardId` и `timing`. Без них не считаются
   бафы, а значит и исход.
2. **`globalInfo`** — счётчики игрока. Большой, но механический объём;
   источники в логе есть, это `BACON_*` теги.
3. **Сырые `tags` и `scriptDataNum1…6`** — дёшево, они уже проходят через
   редьюсер, надо перестать их отбрасывать.
4. **`cleave`, `stealth`, `maxHealth`, `maxAttack`** — мелочь.
5. **Тринкеты и силы героя** — отдельные сущности, в логе видны.
6. **`validTribes`** — племена в партии, в логе `BACON_SUBSET_*`.

Пункты 1–3 стоит сделать до первых замеров точности: без них сравнение
предсказаний с фактическими исходами боёв будет мерить не симулятор,
а полноту нашего маппинга.

Патч 248348 сменил и данные, и правила. Что пришлось сделать и что замерено:

| шаг | было | стало |
|---|---|---|
| снапшот карт | 35 321, не знал 41 карту из 216 в новой партии | 35 714, знает все |
| пакет симулятора | 1.1.726 | 1.1.737 |
| калибровка на партиях билда 246003 | 3.9 п.п. | 9.0 п.п. |
| калибровка на партии билда 248348 | — | **0.2 п.п.**, Brier 0.000 |

Вывод, который стоит держать в голове при каждом патче: **калибровать можно
только на партиях того же билда**. Записанный исход — это факт про ту версию
игры, при которой партия сыграна; после ребаланса он перестаёт быть меркой
для предсказаний, хотя и остаётся годной проверкой разбора лога.

Отдельно про случайность. Тест воспроизводимости («один и тот же вход даёт
один и тот же совет») упал сразу после обновления пакета: три прогона
с зерном 42 дали 57.0, 58.3 и 52.3 процента побед. Причина — не в нашем коде:
с версии 1.1.737 у пакета появился свой источник случайности, и он захватывает
`Math.random` в замыкание при загрузке модуля, поэтому наша подмена глобали,
сделанная позже, на него больше не действует. Теперь зерно задаётся честно —
пакетным `withRng(createSeededRng(seed), …)`. Проверка, выглядевшая
формальностью, поймала молчаливую потерю управления случайностью.


## Тёмные дары (патч 248348) — работают через энчанты, кода не потребовалось

Аномалий в логах нового билда больше нет (`ANOMALY` — 0 совпадений), вместо
них тёмные дары. Дар в логе — обычный энчант: `CARDTYPE=ENCHANTMENT`,
`ATTACHED=<миньон>`, cardId вида `BG36_MidGameEffect_000t61e`. Симулятор
с 1.1.737 реализует 15 таких энчантов.

Наш редьюсер энчанты уже собирал, маппер уже передавал — цепочка сомкнулась
сама. Проверено двумя способами:

- счёт миньонов с энчантом дара в состоянии совпадает с тегом
  `HAS_DARK_GIFT` один в один (part5: 5/5, part6: 7/7, part7: 7/7),
  и у противников дары тоже видны;
- вырезание даров из входа меняет симуляцию: part6 ход 20 — 17.1% побед
  с дарами против 0.0% без. На большинстве боёв разницы нет, и это
  объяснимо: статы дара уже лежат в тегах миньона, а бой-разгром даром
  не сдвинуть.

## Тринкеты — в симулятор и в совет

Прошлый тупик «взятые не отличить от отвергнутых» новый билд снял: взятые
тринкеты видны тегами `BACON_FIRST/SECOND_TRINKET_DATABASE_ID` на героях
**всех восьми игроков**, значение — dbfId. Справочник карт переводит dbfId
в cardId (`infoByDbfId`), маппер кладёт их в `player.trinkets` симулятора —
свои и противника.

Замер на 35 боях патча: расхождение калибровки **5.8 → 5.1 п.п.** после
передачи тринкетов, Brier 0.036 → 0.035. Улучшение скромное, но в нужную
сторону, и оно бесплатное по времени счёта.

Предложение тринкетов (выбор из четырёх) — сущности
`CARDTYPE=BATTLEGROUND_TRINKET` под своим контроллером в `SETASIDE`
с `BACON_TRINKET=1`; на выборе клиент уводит все варианты
в `REMOVEDFROMGAME`, включая взятый. `USE_DISCOVER_VISUALS` маркером
не годится — он стоит лишь у двух вариантов из четырёх (проверено
на сущностях 3371–3374 в part6).

## Ход и Божество (24.09.2026, part71: D286, D287)

**`gameState.currentTurn` — ход ТАВЕРНЫ** (`tavernTurnOf`). Пакет читает его
в двух местах: замок сил «Unlocks on Turn 7» (Drek'Thar `BG22_HERO_002p`,
Vanndar `BG22_HERO_003p`, условие `currentTurn >= 7`) и ограничитель урона
(`damage-cap.js`, `< 4` → 5, `< 8` → 10, иначе 15 — только при переданном
`numberOfPlayersAlive`, см. ниже). До 24.09 туда шёл ход партии, и сила
Drek'Thar отпиралась на четвёртом ходу таверны.

**Потолок урона** (D288, part72) — два поля входа, только вместе:
`gameState.numberOfPlayersAlive` и `options.applyDamageCap: true`. Без
первого пакет потолка не ставит, без второго — не спрашивает вовсе. Число
живых — из таблицы лобби (`playersAlive`: урон героя меньше здоровья;
сдавшемуся игра ставит урон ровно в здоровье, а броню оставляет), в бою

Исхода боя потолок не меняет, только урон, `lostLethal` и перцентили урона.

**Божество — секрет `BG_OldGod`** у героя стороны (пакет с 1.1.757,
`simulation/deity.js`). Поля — теги сигила из лога один к одному:
`scriptDataNum1` — сколько своих аберраций должно умереть (ноль пакет
читает как три), `scriptDataNum2/3` — атака и здоровье тела,
`scriptDataNum6` — dbfId тела (без него — К'Тун). Смерть своей аберрации
пакет узнаёт по ПЛЕМЕНИ из переданных ему карт, поэтому без снапшота,
знающего `ABERRATION` (с 24.09), тело не пробуждается никогда. Механику
`BACON_OLD_GOD` на теле пакет читает, чтобы найти Божество на столе для
прибавок «give your Deity» уже после пробуждения.
