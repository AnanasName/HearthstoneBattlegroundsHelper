# HS Battlegrounds Assistant — ТЗ проекта

## Цель

Десктопный помощник для Hearthstone Battlegrounds, который в реальном времени читает состояние партии из лог-файлов игры и подсказывает наилучшие ходы: оптимальную расстановку миньонов, шансы на исход боя, решения по покупкам и левелингу таверны.

**Никакого компьютерного зрения.** Источник данных — только `Power.log`, который Hearthstone пишет при включённом `log.config`. Никакого чтения памяти процесса, никакой автоматизации ввода (это бан). Оверлей только показывает информацию, все действия в игре выполняет человек.

**Цель — промышленное ПО, а не личная утилита.** Это уже повлияло на решения
и должно влиять дальше: от пользователя нельзя требовать ручных действий вроде
переподключений посреди партии, установка сводится к двум конфигам от инсталлятора,
а приложение само проверяет и чинит настройки при каждом запуске (обновление
Hearthstone может снести `client.config`, он лежит в каталоге игры).

## Стек

- **Язык:** TypeScript (strict mode), Node.js 20+
- **Симулятор боя:** пакет `@firestone-hs/simulate-bgs-battle` (репозиторий `Zero-to-Heroes/api-simulate-battlegrounds-battle`) — не писать свой симулятор, интегрировать готовый
- **Тесты:** Vitest
- **UI (поздние фазы):** Electron, прозрачное always-on-top окно
- **Данные карт:** JSON из HearthstoneJSON (https://hearthstonejson.com), файл `cards.collectible.json` + battlegrounds-теги; закоммитить снапшот в `data/`, не тянуть в рантайме

## Архитектура

```
Power.log → [Watcher] → [Parser] → GameState → [Advisors] → [Overlay/CLI]
                                        │
                          ┌─────────────┼─────────────┐
                     BattleAdvisor  PositionAdvisor  TavernAdvisor
                     (Монте-Карло)  (перебор 7!)     (эвристики)
```

Модули независимы, общаются только через типизированный `GameState`. Каждый модуль — отдельная директория в `src/` со своими тестами.

## Фазы разработки

Работать строго по фазам. Не начинать следующую, пока не выполнен Definition of Done текущей.

### Фаза 1 — Parser + GameState (ядро проекта)

Парсер `Power.log`: tail файла, разбор строк `GameState.DebugPrintPower`, `PowerTaskList`, тегов `TAG_CHANGE` / `FULL_ENTITY` / `SHOW_ENTITY`, сборка `GameState`.

`GameState` минимально содержит:
- фаза партии (выбор героя / таверна / бой / конец)
- номер хода, тир таверны, золото
- свой борд: миньоны с cardId, atk/hp, taunt/divine shield/poisonous/reborn/windfury, golden, enchantments, порядок слева направо
- своя рука и герой (hp + armor, hero power)
- последний увиденный борд каждого оппонента + его hp/tier
- следующий оппонент, если известен

**DoD фазы 1:** для каждой fixture-партии из `data/fixtures/` есть тест, который прогоняет лог целиком и сверяет `GameState` в контрольных точках (заранее размеченных вручную) — состав борда, золото, тир, hp. Все тесты зелёные.

### Фаза 2 — BattleAdvisor

Интеграция `@firestone-hs/simulate-bgs-battle`: маппинг нашего `GameState` во входной формат симулятора, прогон N симуляций (N настраиваемый, старт — 3000), вывод win/tie/loss % и вероятности летала в обе стороны.

**DoD:** на fixture-боях с известным фактическим исходом симулятор выдаёт распределение, где фактический исход не является выбросом; время прогона 3000 симуляций ≤ 2 с на обычном железе.

### Фаза 3 — PositionAdvisor

Перебор перестановок своего борда (≤ 7! = 5040), каждую прогонять сокращённым числом симуляций (например 300), лучшие кандидаты — полным. Выдавать топ-3 расстановки с их win %.

**DoD:** на fixture-состоянии с заведомо важной позицией (клив, poisonous, taunt) советник находит расстановку не хуже той, что была сыграна фактически. Полный перебор укладывается в ≤ 10 с; если нет — beam search.

### Фаза 4 — TavernAdvisor (эвристики, без ML)

Правила: когда левелить (стандартные тайминги по золоту/хп), что покупать (синергия с текущим бордом по племенам и ключевым парам карт), когда реролл. Конфигурация правил — данными (JSON/TS-таблицы), не хардкодом в логике.

**DoD:** unit-тесты на каждое правило + сквозной тест «состояние → рекомендация» на fixture-состояниях.

### Фаза 5 — Overlay

Electron: прозрачное окно поверх игры, показывает вывод советников. До этого — CLI-режим (`npm run watch`), который печатает советы в терминал; CLI остаётся навсегда как режим отладки.

### Фаза 6 (опционально, отдельное ТЗ) — ML

Предсказание финального места по `GameState` на ходу N. Только после того, как фазы 1–5 стабильны и накоплен датасет собственных партий. В этом ТЗ не детализируется.

## Правила работы с логами — критично

1. **Не выдумывать формат `Power.log`.** Формат меняется между билдами игры. Единственный источник правды — реальные логи в `data/fixtures/`. Если в fixtures нет примера нужной конструкции — остановиться и запросить у меня свежий лог, а не угадывать теги.
2. Перед реализацией любого куска парсера — найти соответствующие строки в fixtures и сослаться на них в тесте.
3. Каждая fixture — это `partN.log` + `partN.expected.json` с вручную проверенными контрольными точками. Тесты пишутся от expected-файла.
4. Полезный референс по устоявшимся конструкциям формата — парсеры HearthSim (`hearthstone-deck-tracker`, `python-hearthstone`), но приоритет всегда у фактического содержимого fixtures.

## Правила разработки

- TDD для парсера и советников: сначала тест на fixture, потом код.
- Никаких сетевых запросов в рантайме (кроме опциональной проверки обновлений данных карт по явной команде).
- Каждая фаза завершается работающей демонстрацией: `npm run demo:phaseN` прогоняет fixture и печатает результат.
- Коммиты небольшие, по одному логическому изменению.
- Если задача требует данных, которых нет (лог, ID карты, механика миньона) — спросить, не изобретать.

### Что в GameState

Фаза, ход, тир, золото (остаток и всего), цена и цель подъёма таверны, живая
цена обновления витрины (`rerollCost` — тег кнопки, бывает нулевой), предел
тира, герой с силой, свой борд и рука с полными признаками и энчантами,
магазин с признаком заморозки и живой ценой покупки каждого миньона
(`buyCost` — тег `COST` его кнопки `DragBuy`, part35), борд противника, аномалия, счётчики
`globalInfo`, следующий и текущий противник, накопленные борды соперников
с ходом, на котором каждый снят, таблица игроков лобби (`lobby`:
герой, тир, hp с бронёй и место каждого из восьми), открытое предложение тринкетов
с ценой каждого варианта (`cost` — тег `COST` его сущности), открытый
модальный выбор (`openChoice`: источник и варианты — раскопка, тройка,
лавка), заклинания руки (`handSpells`: цена, место в зоне `zonePos` и значения плейсхолдеров; тем же
типом описаны и заклинания витрины — у них есть признак `costsHealth`,
тег `BACON_COSTS_HEALTH_TO_BUY`: цена такой карты платится здоровьем,
а не золотом),
цена и остаток зарядов тёмного дара (`darkGiftCost`, `darkGiftCharges` —
теги `COST` и `TAG_SCRIPT_DATA_NUM_2` кнопки), плейсхолдеры силы героя
(`hero.heroPowerScriptData` — теги `TAG_SCRIPT_DATA_NUM_1..4` на силе;
у «после N покупок» первый — живой остаток счётчика), замок на силе
(`hero.heroPowerLocked` — тег `LOCK_VISUAL`: сила «Unlocks at Tier N»
до своего тира нажатию не поддаётся, part37),
взятые тринкеты всех игроков (dbfId на героях), карты, виденные в витрине
за партию (`seenShopCardIds` — сырьё состава племён), текущее место
в таблице (`finalPlace`, финальное — на конце партии), номер билда игры
(`buildNumber` — строка `BuildNumber=…` после CREATE_GAME), журнал своих
действий за партию (`actions`: покупки и продажи с картой-целью,
обновления, подъёмы, заморозки, розыгрыши, сила/дар/активации, у каждого
действия — выбранная ветвь модального «Choose One» (`subOption`: 0 первая,
1 вторая, `null` выбора не было) — сырьё
фазы 6).

### Живой режим

Состояние в конце догона — это «сейчас», а не история: обновление приходит
один раз на чтение, после применения всех строк. Правило «на догоне
не советуем» выбрасывало ровно его, и помощник, запущенный посреди партии,
молчал. Закреплено тестом на дописываемом файле.

Живой путь даёт ровно то же состояние, что и пакетный, — это проверяется
тестом на порциях случайного размера, и это единственная защита от их
молчаливого расхождения. Догон файла с начала стоит 234 мс на 41 МБ,
поэтому отдельного быстрого пути не понадобилось. Подробности —
в [docs/live.md](docs/live.md).

**Расстановку в живом режиме почти всегда считать не против кого.** Замер
по всем ходам таверны обеих фикстур: до 13-го хода включительно следующий
противник ни разу не оказался из числа виденных, дальше картинке 7–17 ходов.
Это не дефект реализации — соперников семеро, бой с каждым случается однажды.
Следствие для продукта: советник расстановки в живой игре молчит большую
часть партии, и об этом сказано вслух, а не скрыто.

### Решения, которые НЕ надо переоткрывать

Каждое подтверждено замером или фактурой, ссылки — в `docs/`.

- **Блок темпа таверны говорит ДОСЛОВНОЙ причиной совета подъёма или молчит,
  и вердикта не выносит.** Причин у правила подъёма четыре (отставание
  от кривой, мусорная витрина, «на опережение», порог здоровья
  `levellingHpFloor`), а на пределе тира, без цены в логе и когда подъём
  не по карману, совета нет вовсе — своя склейка на этих точках была бы
  выдумкой, а расхождение подписи блока с советом в списке читалось бы как
  второй, скрытый вердикт. Метки на шкале нейтральные и разной ПРИРОДЫ
  (рамка — вы, подчёркивание — кривая), а не разного цвета: цветом, стрелкой
  или `warn` одна из них становится «правильной». Основание не вкусовое:
  кривая `levelling` — чужие числа, а замер `spike:level` вердикта не выносит
  НАМЕРЕННО (согласие 74% при асимметрии 62 против 24 в сторону игрока,
  и в 47 расхождениях из 61 советник отставания даже не числил). Картинка,
  читающаяся как «вы отстаёте», утверждала бы непроверенное — и вернула бы
  жалобу part20 «очень часто советует улучшить таверну» уже без слов.
- **Длина шкалы тиров берётся от верхнего тира САМОЙ кривой, а не от предела
  тира и не от нынешнего тира игрока.** Тег `BACON_MAX_PLAYER_TECH_LEVEL`
  не встречается НИ В ОДНОЙ из 39 фикстур — ветка редьюсера, которая его
  читает, не срабатывала ни разу, и `maxTechLevel` в жизни всегда `null`.
  Поэтому «рисуем по известный предел» вырождается в «рисуем по ваш тир»,
  а шкала, кончающаяся на клетке игрока, читается как «вы на вершине» —
  прямая ложь на любом ходу партии. Литерала «6» при этом быть не должно
  (второе определение предела тира), и его не нужно: блок рисует кривую,
  значит и показывает её область определения. Известный предел, если он
  когда-нибудь придёт, шкалу только расширяет и гасит клетки выше себя.
- **Порядок узлов в разметке оверлея — это порядок важности, потому что
  переполнение обрезается МОЛЧА.** Окно фиксированной высоты, прокрутки нет
  и быть не может (оно сквозное для мыши и не берёт фокус), поэтому всё, что
  не влезло, пропадает без следа. Значит терять оно обязано снизу: план,
  советы, расстановка, борд, витрина, темп — сначала фон без вердикта, потом
  то, что игрок и так видит в самой игре, и лишь в последнюю очередь
  действенное. Высота 680 взята замером (реальный худший кадр — 592 пикселя,
  при прежних 520 темп обрезался бы целиком), а не «сколько влезет»:
  680 — последнее значение, помещающееся на экране 1366×768.

- **Ряд ВИТРИНЫ на экране — это миньоны И заклинания вместе, по сквозной
  `ZONE_POSITION`** (part41). У нас витрина разложена по типу карты
  (`shop` отдельно, `shopSpells` отдельно), а игра держит её одной зоной
  с общей нумерацией мест. Пока метка оверлея считала состав ряда
  по одним миньонам, ряд из пяти карт числился рядом из четырёх, кольцо
  уезжало на полшага вправо, а у покупки ЗАКЛИНАНИЯ метки не было вовсе —
  два пункта игрока из пяти. Склейка двух списков подряд эту дыру
  не закрывает: нужен ПОРЯДОК, и «заклинание последнее» — догадка,
  которую опровергает сама партия (ход 5: миньоны на местах 1, 2 и 4,
  «Recruit a Trainee» ТРЕТЬИМ; ход 7: четыре миньона и лассо пятым).
  Поэтому у `HandSpell` есть `zonePos`, а ряд собирается объединением
  по нему. Насколько это часто, замерено: 471 точка решения 38 партий,
  заклинание в витрине в 463 из них — то есть кольцо промахивалось почти
  на каждом кадре, просто заметно это лишь на краях ряда. Сквозная
  нумерация 1..N держится в 467 точках из 471; четыре исключения — обе
  СЕГМЕНТНЫЕ партии (part35, part41), артефакт склейки сегментов, а не
  игры: прочитанный отдельно `segment2` даёт чистые 1..7, а живой режим
  сегменты не склеивает вовсе.
- **Порядок вариантов на экране ЛАВКИ АКСЕССУАРОВ знает только канал
  выборов** (part41). У сущностей тринкетов в `SETASIDE` позиции нет
  вовсе — `zonePos=0` у всех четырёх, — а `trinketOffer` собирается
  обходом таблицы сущностей и порядка экрана не хранит: на кадре игрока
  он даёт «Удочка · Чешуя · Копьё · Свеча», тогда как на экране слева
  направо стоят «Свеча · Копьё · Удочка · Чешуя». Строки
  `Entities[0..3]` выбора (`DebugPrintEntityChoices`, источник
  `BG30_Trinket_2nd`) идут ровно как карты на экране. Нет открытого
  выбора — метки нет: зонный путь тринкетов опаздывает (part9: в точке
  решения 3 варианта из 4), и кольцо наугад показало бы на чужую карту.
- **Цвет метки следует СМЫСЛУ у карт и МЕСТУ у кнопок таверны** (part41).
  Кнопка подъёма сама зелёно-золотая, а вокруг обновления и заморозки
  игра рисует СВОИ зелёные рамки доступности — зелёное кольцо покупки
  на них теряется дважды (жалоба игрока: «обводка для поднятия таверны
  довольно сильно сливается по цвету»). У кнопок смысл действия назван
  словом прямо в подписи («ПОДНЯТЬ ТАВЕРНУ · 4», «ОБНОВИТЬ · 1»,
  «ЗАМОРОЗИТЬ»), поэтому им отдан отдельный тон `tavern`; у карт же цвет
  — единственное различие покупки и продажи, и там тона остались
  смысловыми.
- **«Боевой раж», платящий КАРТОЙ, решается тай-брейком среди
  НЕРАЗЛИЧИМЫХ расстановок, а не весом** (part41, `rallySwing.ts`).
  Раж срабатывает при АТАКЕ носителя, а атакуют слева направо; замер
  счётчиком на реализации карты в пакете симулятора (Bronze Timewalker
  `BG36_242`, поле из пяти виденных бордов, 10 000 боёв на расстановку):
  с 1-го места раж сработал 10 000 раз из 10 000, с 5-го — 102, со
  2-го — 2 813. В исходе боя это не весит НИЧЕГО: симулятор кладёт добычу
  в руку и возвращает `dmgDoneByAttacker = 0`, — то есть советник платил
  картой за доли пункта, сам того не зная (жалоба игрока: «предлагает
  поставить карту с боевым ражем на 5 место, кажется, что он почти
  никогда не сработает»). Курса «карта в руке → проценты боя» у нас нет
  и выдумывать его нельзя — тот же долг, что у `spike:hand` и платного
  края борда (part39). Поэтому веса не тронуты, а меняется только выбор
  между расстановками, которые наша же мерка признала неотличимыми:
  из них берётся та, где носитель левее. Что это именно случайный бросок,
  видно из пяти прогонов на одной точке ДО правки: ражник вставал то
  первым, то вторым, то пятым при приросте 0.2–0.8 п.п.; после правки все
  пять ставят его вторым с тем же приростом, и срабатывание возвращается
  с 0.01 до 0.28 на бой. Когда мерка РАЗЛИЧАЕТ расстановки, совет
  не меняется — вместо этого строка называет цену («Bronze Timewalker
  1→2: «раж» срабатывает при АТАКЕ носителя, а карту в руку бой
  не считает»), и решает игрок. Класс узкий и назван: ражем владеют
  32 миньона пула из 395, картой платят восемь; ражи со словами «this
  game» НЕ берутся намеренно — часть их эффекта симулятор применяет
  внутри боя.

- **От исполнителей принимаются СЫРЫЕ Power.log, а не записи датасета**
  (решение 28.08, docs/collector.md). Запись датасета — производная
  от редьюсера той версии, что стояла у игрока, а редьюсер меняется
  еженедельно (`lobby` 18.08, `actions` 19.08, `heroPowerScriptData`
  28.08); запись старой сборки не обновить, лог перечитывается любой
  версией — это и делает `dataset:backfill`. Лог жмётся в двадцать раз
  (part33: 28.8 МБ → 1.44 МБ), не зависит ни от версии приложения,
  ни от снапшота карт, и годится в фикстуру как есть. Записи
  генерируются у нас командой `dataset:import`, с полями `contributor`,
  `contributorRating` (со слов — в логе рейтинга нет) и `overlay`.
- **Пути данных считаются от собственного модуля и от `resourcesPath`,
  а не от рабочего каталога** (`src/app/paths.ts`). Строки вида
  `data/cards/…` верны только при запуске из клона репозитория; у сборки
  рабочий каталог произвольный, а Program Files не пишется — рекордер
  датасета упал бы молча (у GUI-сборки нет stdout). Из репозитория оба
  корня — `data/`, из сборки данные — `resources/data`, записи —
  `%LOCALAPPDATA%\hs-bg-assistant`. Признак сборки — снапшот карт
  в `process.resourcesPath` (под Electron без сборки тот указывает
  в `node_modules`, и это честно «репозиторий»), не `app.isPackaged`:
  пути нужны CLI, воркеру и тестам.
- **Каталог установки игры лежит в реестре в ветке удаления программ**
  (проверено 28.08): `HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\
  CurrentVersion\Uninstall\Hearthstone` → `InstallLocation`. Веток
  `Blizzard Entertainment` в HKLM/HKCU нет; `Battle.net.config` знает
  путь к Battle.net, не к игре. Порядок: явный путь → реестр (каталог
  обязан содержать `Hearthstone.exe`) → перебор типичных каталогов
  по дискам → прежняя константа, чтобы «логов не нашлось в …» называло
  конкретный путь.
- **Флаг «шёл ли оверлей» пишется в каждую архивную сессию и доезжает
  до записи датасета.** Партия по подсказкам — не «как играют люди»
  (второй контур петли, docs/ml.md); у исполнителя оверлей выключен
  по умолчанию и включается галочкой в трее. `Ctrl+Shift+Q` выключает
  оверлей, а не приложение — сборщик продолжает работать.
- **`client.config` в сборке правится повышенным экземпляром через UAC
  (`--setup`), а инсталлятор делает то же сразу после установки.**
  Говорить исполнителю «запустите от администратора» — значит, что он
  этого не сделает, лог оборвётся на 10 МБ, и партия на приёме уйдёт
  в «обрыв». Хук — `build/installer.nsh`; команда PowerShell
  (`Start-Process -Verb RunAs -Wait -PassThru`) собирается функцией
  и проверена тестом на кавычки.
- **Ключ кэша обязан покрывать ВСЁ, от чего зависит ответ, — иначе первый
  спросивший отвечает за всех.** Советник кэширует дорогое дважды:
  разбор текста карты (`memoByCard`) и ожидание по пулу тиров
  (`averagePoolValue`, сотня `minionValue` на вызов). Первый ключуется
  правилами, справочником и картой; второй — теми же правилами
  и справочником, ссылкой на массив борда и СТРОКОЙ из всего остального:
  состав руки (копии считаются и по ней), заклинания руки (слагаемое
  магнита), сила героя (её текст входит в ценность покупки с part22).
  Прежний ключ знал только тиры и ДЛИНУ руки, и опаснее всего был третий
  случай: розыгрыш заклинания руки не меняет НИ ссылки на борд
  (`withoutMagnetCharge` возвращает тот же массив, когда заряд не тратится),
  НИ длины руки — ключ выходил буквально тот же, и следующий шаг плана
  считал планку заморозки и тёмный дар по состоянию, которого уже нет.
  Правило общее: кэш — это утверждение «ответ зависит только от ключа»,
  и проверять его надо списком аргументов той функции, что под кэшем,
  а не тем, что менялось в голове при написании.
- **Счётчик, который читают ПО ЗАПРОСУ, обязан считать тот, кто
  спрашивает.** `spellMagnetGain` читает дневной заряд хранителя
  из `scriptData[0]` самого миньона и потому на всех вопросах отвечает
  одинаково. Ценность покупки складывала выгоду по всем заклинаниям руки
  — два трезубца давали +4 стата вместо +2, — а план списывал заряд
  через `scriptData.map`, который на ПУСТОМ массиве не делает ничего:
  ровно в том случае, который обе стороны читают как «тег не проставлен,
  значит заряд есть». Обе половины чинятся одинаково — вести счёт
  на стороне спрашивающего и писать заряд по индексу, а не отображением.
- **`grantsGold` — ВАЛОВОЕ золото из текста, потому что цену

- **Число, которым СОРТИРУЮТ список, число, которым ОТБИРАЮТ кандидата,
  и число, которым СКЛАДЫВАЮТ цепочку, — ТРИ разных числа.** У прокрутки

  ценнее». Пока оба жили в одном поле, слабый генератор выигрывал отбор

  при сгорающей монете против 12.00 у линии, которую игрок сыграл сам
  и которая тратила всё, — то есть ровно на величину бампа. Развилка
  сгорающего золота (part23) при этом отработала ЧЕСТНО: запустилась,
  взяла линию игрока в альтернативы и проиграла ей же, потому что
  сравнивала числа с разной начинкой. Лечится `standaloneScore` —
  тем же полем, что у подъёма (part25), и без единого нового веса;

  `min(2 + N, 10)`: наш `turn = 15` — восьмой ход таверны с десятью
  золотыми, а не пятнадцатый ход партии. Сравнение таблицы `levelling`
  с сырым `turn` разгоняло кривую вдвое: «тир 6 с хода 11» читалось
  как «с ШЕСТОГО хода таверны», где восемь золота и тир 6 недостижим
  в принципе, — и советник числил отставание в 87% точек решения, ставя
  подъём верхним советом в 50% (жалоба part20 «очень часто советует
  улучшить таверну»; после `tavernTurnOf` — 45% и 30%, замер
  `npm run spike:level`). **Перезамер 05.09 на 38 партиях (471 точка):
  42% и 27% — четвёртый прогон подряд с теми же числами** (на 36 партиях,
  445 точек, было то же самое). На 32 партиях (02.09) было 43% и 28%, причём на новых
  девяти партиях заметно реже — 36% и 26% против 46% и 28%
  на part4–part26. Правило общее: числа, взятые из разговоров
  об игре и чужих таблиц, живут в ходах таверны и переводятся; числа,
  ЗАМЕРЕННЫЕ у нас (`trinketOfferTurns: [11, 17]`), живут в нашей
  нумерации и перевода не хотят. Совет обязан называть ход в той шкале,
  в которой считает, — иначе игрок не может сверить причину.
- **РУКА идёт в симулятор вместе с бордом.** Часть карт пула играет рукой
  прямо в бою: «Rally: Summon the highest-Attack minion from your hand for
  this combat only» (Expert Aviator), «Whenever this takes damage, give
  a minion in your hand +2/+1» (Very Hungry Winterfinner). Симулятор это
  УМЕЕТ (`expert-aviator.js` читает `attackingHero.hand`), а маппер руку
  не передавал вовсе — и строка «по бою» оценивала носителя ралли как голое
  тело: на part21 (ход 5) мурлок давал 77.4% вместо 97.0%. Миньон руки
  обязан нести `maxHealth`: кандидатов на призыв симулятор отбирает
  условием `!!e.maxHealth`, а тег в руке бывает пустым. Поле `playerHand`
  необязательное — у старых эпизодов руки нет, и отсутствие честнее пустого
  списка. Пороги калибровки правка не сдвинула.
- **«Временное» усиление ищется в СВОЁМ предложении, а не по всему тексту.**
  У Undersea Mount «Give a minion +{0}/+{1}. If it's a Naga, also give it
  Windfury until next turn» временна только вихревая половина, статы
  постоянны. Поиск слов по всей карте объявил бы временными и их — тот же
  класс тихой ошибки, что склеенный золотой текст (part17) и сложенные
  ветви «Choose One» (part19). Временных чародейских токенов в пуле пять
  из 22, среди 206 заклинаний витрины — три со статами.
- **Магнит заклинаний бьёт «крупнейшее тело» при выборе цели** (part21,
  ход 9). Магнит — миньон, чей текст говорит о заклинании, применённом
  К НЕМУ; таких в пуле семь. Выгода считается ЧИСЛОМ и только там, где
  число есть: у ХРАНИТЕЛЯ (Lava Lurker, «The first Spellcraft spell played
  from hand on this each turn is permanent») это временная часть усиления,
  которая станет постоянной (+2 у Mini-Trident), у РАСТУЩЕГО (Fleeing
  Fugitive, «gain +{0} Health») — его собственный плейсхолдер (+1). Двойка
  против единицы и сменила цель. Остальным пяти магнитам выгода честно
  равна нулю, и цель у них выбирается как прежде: «не берёмся судить»
  лучше выдуманного веса. Чародейское заклинание опознаётся соглашением
  идентификаторов `<id миньона>t` (проверено на всех 22 чародеях пула),
  дневной заряд хранителя — живым тегом `TAG_SCRIPT_DATA_NUM_1`
  («({0} left!)»), и план тратит его один раз за ход.
- **Заклинания РУКИ идут в ценность покупки магнита из витрины** (part21,
  ход 5). Три заклинания в руке при беглеце в витрине — это +3 стата
  навсегда, и связь читается из состояния. Своего веса у слагаемого нет
  намеренно: выгода измерена в статах, а у статов цена уже есть. Верхней
  покупкой беглеца это не сделало (9.0 против 10.0 у мурлока, и по бою
  55.1% против 97.0%) — слагаемое добавлено потому, что оно ЕСТЬ, а не
  потому, что должно было перевернуть совет.
- **Провокация на носителе ралли — ЗАМЕРЕНО четырежды, разницы не видно,
  и знак у неё сменился на третьем прогоне.** Довод игрока (ралли
  срабатывает при АТАКЕ носителя, а провокация зовёт на него удары —
  можно не дожить) проверялся замером, а не мнением; предрегистрация
  закоммичена до первого прогона и не менялась. Основная пара (двигается
  только провокация): 62 точки 18 партий — −0.332 при пороге 0.448;
  78 точек 23 партий — −0.241 при 0.359; 112 точек 32 партий — +0.203
  при 0.360; **123 точки 33 партий — +0.165 при 0.333** (03.09).
  Правила нет. Прежде знак стоял «в сторону опасения игрока» и это
  отмечалось вслух — теперь он в противоположную сторону, ни на шаг
  не приблизившись к порогу: у величины внутри шума знак и есть шум.
  Седьмой прогон (04.09, 35 партий): 138 точек, +0.020 при пороге 0.338;
  восьмой (04.09, 36 партий) и девятый (05.09, 37 партий) дали
  ТОЖДЕСТВЕННЫЕ числа, и это не сбой — part39 сыграна на мехах, part40
  на пиратах, и обе дали замеру РОВНО НОЛЬ точек, то есть выборка
  не росла вовсе. ДЕСЯТЫЙ (05.09 ночью, 38 партий) сдвинулся, потому что
  part41 принесла ЧЕТЫРЕ точки: 142 точки, **−0.057 при пороге 0.343**,
  и знак сменился в очередной раз. Замер растёт только партиями
  с носителями ралли, и это стоит помнить, планируя следующий перезапуск.
  Читать как «польза не показана»: у 92 точек из 123 обе ветви дали
  тождественный исход, эффективная выборка мала. Замер стал возможен
  только вместе с передачей руки — до неё ралли-призыв не срабатывал вовсе.
  Перезапуск — `npm run spike:taunt`.
- **Цена подъёма таверны читается из лога, таблицей её не заменить.** Тег
  `COST` кнопки `TB_BaconShopTechUp0N_Button`. Цена падает на единицу за
  каждый ход без подъёма, то есть зависит от всей истории партии.
- **Цена ОБНОВЛЕНИЯ витрины — тоже живой тег, и ноль там значащий.** Тег
  `COST` кнопки `TB_BaconShop_8p_Reroll_Button`; правилом игры это единица,
  но обновление бывает бесплатным целый ход, и это не редкость — шесть партий
  из четырнадцати: заклинание «Leaf Through the Pages» («Gain 2 free
  Refreshes» — part6 ходы 17–21, part7, part8, part13, part17), напарник
  Magnus Manastorm («Two Refreshes each turn are free» — part12 с хода 15),
  экономические тринкеты. Советник считал по таблице и в такие
  ходы был честно неправ: реролл уступал подъёму, которому не отнимал ни
  монеты. Сброс кнопки в начале хода нулями отсеян зоной — на это время
  сущность лежит в `REMOVEDFROMGAME`, а не в `PLAY` (замерено на всех
  14 партиях билда). Это же закрывает и «экономические эффекты тринкетов»:
  цену покупки (`BACON_REDUCE_BUY_COST`), подъёма, обновления и заклинаний
  игра считает сама, а мы читаем результат.
- **Заморозка соревнуется с бесплатным обновлением, а не с пустотой.**
  Незамороженная витрина обновляется в начале хода даром, поэтому морозить
  можно только то, чего свежая витрина не обещает: копию под тройку или
  собираемое племя. Абсолютный порог ценности это правило уже ломал.
- **Порог «выбор что-то решал» в сверках обязан превышать шум Монте-Карло.**
  Порог 1 п.п. при ошибке разности ~1.6 п.п. давал множество «решающих»
  ходов, состав которого зависел от зерна: 33% совпадений при 800 симуляций
  против 62% при 2000 на одних и тех же партиях.
- **Точка решения в таверне — последнее состояние до первой траты золота.**
  Не первое: витрина наполняется не мгновенно, и снимок заставал в ней одного
  миньона вместо пяти. Не конец фазы: там золото всегда 0 из 10.
  **С 29.08 — состояние ПЕРЕД ДЕЙСТВИЕМ, которое тратит** (решение игрока
  после замера в docs/collector.md): прежний снимок на последнем
  `ZONE`/`RESOURCES`-событии отставал от живого пути на усиления тегом
  `ATK` без смены зоны (part7: атака 44 против 48), тир соперников
  в `lobby` и закрытый выбор тринкета. Граница — НАЧАЛО верхнего блока,
  а не строка `RESOURCES_USED`: трата приходит внутри блока PLAY, и флаг
  «сила нажата» ставится на BLOCK_START строкой раньше (part30) — снимок
  перед самой тратой попадал внутрь действия и ронял part11. Строки
  BLOCK_START событиями не являются, первое событие блока несёт стек
  с тем же объектом верхнего блока, по нему и ловится начало; трата вне
  блоков (тринкет за золото, part32) — перед самим событием. Живой путь
  (`DecisionPoints` на конце порции) не менялся: пакетное определение —
  каноническое, живое зависит от границы порции.
- **Применение силы героя и тёмного дара видно только блоком `BlockType=PLAY`
  на их сущностях.** `EXHAUSTED` на силе впервые встретился в part32
  («Ритуал перерождения»: 1 после нажатия, 0 в начале хода) — это
  подтверждение, а не источник: у прочих сил тега нет (part8: 10 нажатий
  силы — 10 блоков, ни одного `EXHAUSTED`). Сброс «нажато в этом ходу» — по смене `TURN`.
  Недоступность силы — тег `LITERALLY_UNPLAYABLE`; он же блокирует карты
  в руке (замок тринкета), и «разыграть» такие не советуется.
- **Порог реролла обязан расти с тиром.** Плоский порог к пятому тиру
  не срабатывал никогда: миньон там дороже порога одним тиром.
- **У тринкета есть ЦЕНА, и внутри одного предложения она РАЗНАЯ** (тег
  `COST` его сущности; замерено 02.09 на part32, ход 17: при десяти
  золотых четыре варианта стоят 4, 5, 5 и 2). Совет её называет вместе
  с остатком («2 золота, останется 8»): точка решения показывает золото
  ДО выбора, и без этого план строился на золото, которого сейчас же
  не станет. В РАНЖИРОВАНИЕ цена не входит намеренно — сколько мест
  стоит золотой на этом ходу, у нас не замерено, а выдуманный
  коэффициент перевернул бы порядок, подтверждённый игроком
  (`trinketPlacePerTribeMinion`, docs/jeefhs.md). Тега `COST` иногда нет
  вовсе — тогда `cost: null`, и цена не называется.
- **Взятые тринкеты читаются с героев, а не из зоны.** Теги
  `BACON_FIRST/SECOND_TRINKET_DATABASE_ID` (значение — dbfId) видны у всех
  восьми игроков. Маркер открытого предложения — `BACON_TRINKET=1`
  в `SETASIDE`; `USE_DISCOVER_VISUALS` не годится, он лишь у части
  вариантов. На выборе все варианты уходят в `REMOVEDFROMGAME`.
- **Цель-поле не трогает поиск: симуляции кандидата делятся между бордами
  поровну, счётчики складываются.** Это послойная выборка среднего по полю;
  накопление, финал и значимость работают на слитых счётчиках как на одном
  борде. Замерено (`npm run spike:field`): постоянная часть вызова множится
  на K (13 → 82 мс на кандидата при K=1 → 7), охват отбора падает до ~30
  кандидатов — и это принято, потому что ландшафт среднего исхода глаже
  одиночного (размах 0–2.5 п.п. против десятков). Следствие заявлено:
  против поля советник чаще честно говорит «менять нечего». Взвешивать
  борды по свежести не стали — данных о том, кто вероятнее выпадет, нет.
- **Сверять покупки против последнего увиденного борда противника нельзя.**
  Он устаревает на 7–17 ходов, все сравнения выходят разгромом 100:0,
  а разброс между кандидатами — тождественный ноль. Для сверки берётся борд,
  который вышел в бою следующего хода на самом деле.
- **Модальные выборы — канал `DebugPrintEntityChoices`/`SendChoices`,
  не зоны.** Раскопка, награда за тройку, лавка аксессуаров — всё приходит
  заголовком с id и строками `Entities[i]` с cardId; закрытие — `SendChoices`
  с тем же id. Id вариантов НЕ совпадают с id зонных копий тех же карт,
  зонный путь тринкетов опаздывает (3 из 4 вариантов в точке решения part9),
  выбор героя идёт тем же каналом с `ChoiceType=MULLIGAN`. Строки каналов
  выбора нельзя пропускать через стек блоков — их отступ чужой. Фактура
  в docs/power-log.md.
- **Ключи племён в таблицах правил — строки `races` снапшота.** Племя
  механизмов называется `MECH`; ключ `MECHANICAL` не совпадал ни с чем,
  и тринкет про мехов при пяти мехах на борде получал «своих таких нет»
  (part9, скриншот). Список рас пула: ALL, BEAST, DEMON, DRAGON, ELEMENTAL,
  MECH, MURLOC, NAGA, PIRATE, QUILBOAR, UNDEAD.
- **Шаблоны «сила даёт миньона» обязаны терпеть местоимение и синонимы.**
  У Зиреллы «Choose a minion in the Tavern. … and add it to your hand» —
  «minion» и глагол в разных предложениях (part9, ход 3). У E.T.C.
  «Discover a Buddy» — слова «minion» нет вовсе (part12). Словарь
  пополняется по фактам таких промахов.
- **Племя тринкета — тег `BACON_SUBSET_<RACE>` на его сущности, текст
  вторичен.** У «Разноцветного компаса» племя в тексте — плейсхолдер `{0}`,
  и текстовый разбор его не видел (part12).
- **Имена в тегах `BACON_SUBSET_*` совпадают с племенами снапшота
  НЕ ВСЕГДА, и приводит их редьюсер** (`raceOfSubsetTag`, таблица
  `SUBSET_TAG_RACES`; part36). Восемь имён из десяти сходятся (BEAST,
  DEMON, DRAGON, MECH, MURLOC, NAGA, PIRATE, UNDEAD) — и потому
  расхождение двух прожило от part9 до 03.09 незамеченным: игра пишет
  `QUILLBOAR` с двумя «l» и `ELEMENTALS` во множественном числе, а снапшот
  знает `QUILBOAR` и `ELEMENTAL`. Сравнение с бордом молча не совпадало
  никогда, и выглядело это честной фразой «своих таких нет» при пяти своих
  на столе (жалоба игрока, ход 17: тринкет `BG36_MagicItem_214` при пяти
  квилбоарах). Таблица, а не правило словообразования: `UNDEAD` уже без
  «s», `MECH` короче любого правила. Незнакомое имя проходит как есть —
  новое племя патча лучше показать сырым тегом, чем потерять, — и ловится
  это тестом, который сверяет КАЖДЫЙ тег партии со списком племён
  снапшота. `TrinketOffer.subsetRaces` по договору хранит племена
  снапшота: читателям про имена тегов знать незачем.
- **Цель заклинания-усиления — поле рекомендации, а не слова в reason.**
  Оверлей показывает короткую строку действия, и совет без цели
  перекладывал выбор на игрока (part12). **То же и у ОБНОВЛЕНИЯ
  витрины** (`searchGoal`, part37): правило part27 крутит витрину при
  нуле золота только под названную цель заморозки — и называло её,
  но в `reason`, которого на экране нет. Игрок видел голое «ОБНОВИТЬ»
  при нуле золота и полном борде и возражал совершенно справедливо:
  «купить всё равно не на что». Правило было право, а на экране от него
  не оставалось ничего. Общее правило: факт, без которого совет читается
  НЕВЕРНО, живёт полем и попадает в строку действия; в `reason` остаётся
  арифметика.
- **Магнитный мех на полном борде не требует продажи.** `mechanics: MODULAR`
  в снапшоте; совет называет носителя — самый крупный свой мех. Прежний
  совет «разыграть магнита, продав N» отдавал миньона даром (part9, ход 13).
- **Тип карты в снапшоте пишется смешанным регистром** («Minion»,
  «Battleground_trinket») — сравнение без нормализации молча не совпадает
  никогда. Справочник приводит к верхнему регистру.
- **На полном борде покупку ОПЛАЧИВАЕТ продажа, и золото считается вместе
  с ней** (part36, ход 13). Покупка туда всё равно идёт через продажу
  слабейшего, а продажа приносит золотой — значит, бюджет равен
  `gold + sellGold`, а не `gold`. Обе стороны размена молчали по одной
  причине: `buyRules` отбрасывал миньона фильтром «цена ≤ золота» ещё
  до ветки «борд полон, продать X», а `sellRule` возвращал `null`
  условием «лучший не по карману» — хотя лучший покупается ПОСЛЕ той
  самой продажи, которую правило и советует. На скриншоте после подъёма
  на тир 5 осталось 2 золота при витрине по три: оверлей сказал
  «ОБНОВИТЬ за 1» и «НИЧЕГО», а игрок продал Water Droplet (5.0) и купил
  Fearless Foodie (18.5). Прибавка идёт ТОЛЬКО ветке с продажей: тройка
  сливается сама, вторая копия уходит в руку, магнит садится на носителя —
  там продавать некого. Тот же счёт — в фильтре плана: шаг с `sellFirst`
  платит за себя возвратом, как это уже делал `applyRecommendation`.

  **На СИЛУ ГЕРОЯ прибавка распространена 05.09 (part40, ход 13).** Золото
  1, борд полон, сила стоит 2, оверлей печатал одно «НИЧЕГО» — а игрок
  продал Southsea Busker и нажал силу (лог, 20:04:11). Довод тот же, что
  у покупки, и он структурный: найденный силой миньон приходит В РУКУ,
  на полном борде место ему освобождает продажа, и `handMinionVictim`
  уже стоял в этом же правиле строкой ниже, вычитая ценность жертвы, —
  не хватало только того же слагаемого в кошельке. Границы те же:
  `victim` не пуст ТОЛЬКО на полном борде, поэтому «продать ради монеты»
  правило не советует, а поле `sellFirst` заполняется лишь тогда, когда
  без продажи силу НЕ НАЖАТЬ. Вторая половина правки обязательна
  и без неё первая была бы враньём: `applyRecommendation` в ветке
  `heroPower` про `sellFirst` не знал вовсе — шаг стоил бы золота,
  которого нет, а жертва осталась бы на борде.

  **На ПОДЪЁМ эта прибавка НЕ распространена, и это проверено, а не
  забыто** (part39, ход 5: игрок продал свинобраза и на вырученную монету
  поднял таверну за 6 при пяти золотых). Привратник `cost > state.gold`
  золота от продажи действительно не видит, но правка ИНЕРТНА:
  на точке решения подъём и так по карману (снимок стоит ПОСЛЕ продажи —
  продажа не тратит) и стоит РОВНО НОЛЬ очков, потому что таверна идёт
  по графику; по 445 точкам 36 партий клеток «подъём не по карману,
  но продажа его открывает» ровно 36, и отставания от кривой нет ни
  в одной; оверлей печатает три строки, а подъём с нулём стоит шестым
  из семи. В ЕДИНСТВЕННОЙ клетке корпуса, где правка что-то двигает
  (part5, ход 5), на борде ОДИН миньон — совет вышел бы «продать своё
  единственное тело ради тира». Вдобавок `applyRecommendation` знает
  `sellFirst` только в ветках `buy` и `play`: у `levelUp` шаг дал бы
  золото −1 с жертвой, оставшейся на борде, — то есть это уже смена
  механики плана, а не чтение факта. Настоящая причина расхождения —
  КРИВАЯ подъёма, прямая цена решения игрока от 17.08 (part25), принятого
  после трёх его же жалоб в обратную сторону; жалобе место в столбце
  «только игрок» замера `spike:level`, а не в списке дефектов.
- **Позиционные ТРИНКЕТЫ не читаются вовсе, и на part39 это ИНЕРТНО —
  но подача всё равно должна называть платный слот.** Emergency Gearblade
  `BG36_MagicItem_812` («At the end of your turn, cast Repair Job on your
  left-most Mech») делает КРАЙНИЙ ЛЕВЫЙ слот слотом выплаты, куда каждый

  носителей только среди МИНЬОНОВ БОРДА и только по шаблону «adjacent

  симулятор этот тринкет не реализует (эффект тавернный, а не боевой);
  а ТЕКСТ своих тринкетов не читает ни одно правило — все читатели

  ЕДИНСТВЕННОЙ мерке проекта советник прав, и прав именно ПОСЛЕ учёта
  тринкета: с применённым +4/+8 крайнему левому (4000 симуляций против

  игроком — 92.6 %, «кэрри первым» — 93.3 %; +4/+8 на теле 7/3 (→ 11/11)

  одобренный порядок возразить не даёт, а это доктрина `searchGoal`

  часть таких эффектов симулятор считает сам, и обещать про них

  Sticker), и без `\s*` карта терялась бы молча — тот же класс тихой

- **На полном борде ценность кандидата считается против борда БЕЗ жертвы,

- **У заклинаний ДВА типа: в руке SPELL, в витрине BATTLEGROUND_SPELL.**

- **Заряды тёмного дара — `TAG_SCRIPT_DATA_NUM_2` на кнопке.** Три на

- **Энчант `TB_BaconShopBadsongE` значит лишь «розыгрыш бесплатен»,

- **Бафф «соседям» конца хода применяется к кандидатам расстановки
  ПЕРЕД симуляцией** (`battle/endOfTurn.ts`, part16). Порядок фаз:

- **Батлкрай-генератор карт можно прокрутить: купить-разыграть-продать

- **Счёт обещанных карт пишется и СЛОВОМ, и ЦИФРОЙ, и читать надо оба**

  и купить ещё одно существо»); журнал партии повторяет её дословно.

- **Прокручивается и ПРОДАЖНЫЙ генератор — тот, у которого платит

- **Витрина держится ради продажного генератора по планке заклинания**

  **Запрета `justLevelled` у этой ветки нет НАМЕРЕННО, и переоткрывать
  его не надо** (проверено разбором кода 18.08). Ветке ПЛЕМЕНИ запрет
  нужен потому, что её порог — число от тира из таблицы правил
  (`2 × тир + запас`), и подъём его не двигает: без явного `mates = 0`
  витрина держалась бы ради соплеменника, которого свежая витрина нового
  тира предложит и так. У прокрутки и заклинания порог другой —
  `spellThresholdOf`, то есть ожидание по тирам ВИТРИНЫ
  (`averagePoolValue(shopTiers(state.techLevel))`), а `techLevel`
  в ход подъёма уже НОВЫЙ (редьюсер ставит `techLevelUpTurn = turn`
  тем же тегом, которым меняет тир). Планка поднимается сама, ценность
  прокрутки остаётся на обещанном текстом тире — и ветка гаснет
  арифметикой, а не запретом. Второй запрет поверх этого был бы
  правилом без фактуры.
- **Тексты снапшота переносят строки посреди предложения** — многословные

- **Совпадение с симулятором честно считать «попал в ЛЮБОЙ максимум».**
  Ничьих за первое место 66 из 108: счёт «по первому максимуму» бесплатно
  награждает исходный порядок и вдвое преувеличивает падение
  (64% против честных 78%).
- **В ход подъёма таверны заморозка ради ПЛЕМЕНИ молчит.** Свежая витрина

  17.08 (part23).** Читать надо пункт «Заморозка ради заклинания судится
  ЦЕНОЙ» ниже: маржинальная форма (`threshold − bestKept`) сравнивала
  числа с разной начинкой и на собранном борде падала в ноль. Запись
  оставлена, чтобы довод «заморозка — ДОПОЛНИТЕЛЬНОЕ действие, а не замена
  покупке» не переоткрывался как новый: он верен, но планку из него

- **Активность силы героя — тег `HAS_ACTIVATE_POWER` на её сущности; цены

  бесплатные условием `cost > 0`, и сила Хроми «Refresh the Tavern» молчала
  всю партию (part13). Советуется только бесплатная И активная сила

- **Сила «Unlocks at Tier N» под замком — тег `LOCK_VISUAL`, и по прочим
  тегам она НЕОТЛИЧИМА от доступной** (part37). У «Королевы драконов»
  Алекстразы (`TB_BaconShop_HP_064`, «Discover a Dragon. *(Unlocks at
  Tier 4.)*») с первого хода стоят `HAS_ACTIVATE_POWER=1` и `COST=1`,
  а `LITERALLY_UNPLAYABLE` — тег, которым правила проверяли «жать
  нельзя», — не приходит НИ РАЗУ. Поэтому советник пять точек решения
  подряд (ходы 1–9) ставил её ВЕРХНЕЙ строкой и первым шагом плана,
  предлагая действие, которого игра не давала. `LOCK_VISUAL=1` приходит
  блоком TRIGGER сразу за созданием силы и снимается в ноль ровно
  на подъёме до нужного тира (21:21:26, в тот же миг, что
  `PLAYER_TECH_LEVEL=4`); тег общий для «кнопок под замком» — та же пара
  стоит на кнопке тёмного дара до пятого хода. Причину игра называет
  своим каналом (`DebugPrintOptions`,
  `error=REQ_MINIMUM_TAVERN_TIER_LEVEL_TO_PLAY`), но читать надо ФАКТ,
  а не причину. Три запрета («нажата в этом ходу», `LITERALLY_UNPLAYABLE`,
  `LOCK_VISUAL`) собраны в `heroPowerReady`: прежние два жили копиями
  в пяти правилах силы, и третий, добавленный в четыре места из шести,
  разъехался бы молча. По маркеру опций проверены все 33 партии списка:
  сила под замком стояла только в part37 и part12 (E.T.C., «Discover
  a Buddy. *(Unlocks at Tier 2.)*», первые два хода).
- **Сила, ДАЮЩАЯ ЗОЛОТО, читается кубиком из текста, а её КУЛДАУН уже
  читался и слепотой не был** (part39, Змеиный Глаз `BG28_HERO_400`,
  «Удачный бросок» за 1: «Roll a 6-sided die. Gain that much Gold.
  *(Cannot be used again for that many turns!)*»). Советник молчал про неё
  все десять точек решения партии, и дыра оказалась ЧИСТО ТЕКСТОВОЙ:
  разбор золота требовал ЦИФРУ («gain \d+ gold») и «that much» не видел —
  тот же класс, что счёт словом против цифры в part38. Число ГРАНЕЙ
  берётся из текста группой шаблона (`heroPowerGoldWords`), ожидание —
  `(N+1)/2`, то есть арифметика названного кубика, а не подобранный
  коэффициент. Шаблон привязан к ГЛАГОЛУ броска: свободный поиск слова
  «Gold» прочитал бы «Minions and Refreshes cost 2 Gold» как прибыток.
  По пулу канал ловит 2 карты из 174 при 17 упоминающих золото; плоская
  форма «Gain N Gold» остаётся немой до фикстуры (у Piggy Bank сумма
  РАСТЁТ, живого числа мы не видели, а без проверки позиции шаблон
  проглотил бы весь класс «After you …, gain N Gold»).
  **Кулдаун нового канала не потребовал, и это половина, которую легко
  принять за дефект:** он РАВЕН выпавшему числу, и на перезарядке игра
  подменяет сущность силы — вместо `BG28_HERO_400p` (COST=1,
  `HAS_ACTIVATE_POWER=1`) стоит `BG28_HERO_400p2` с `LOCK_VISUAL=1`, без
  цены и без активности, а остаток ходов живёт в `TAG_SCRIPT_DATA_NUM_1`
  (5→4→3→2→1→0 по ходам ТАВЕРНЫ). `heroPowerReady` (part37)
  и `heroPowerHasActivate` (part13) уже давали верный ответ: сила
  по-настоящему открыта ровно в ОДНОЙ точке решения из десяти — на том
  самом ходу, где игрок её нажал и на который пожаловался.
  **Два числа для двух вопросов:** в СПИСОК идёт ожидание
  (`(3.5 − 1) × goldPointValue = 7.5`), в ПЛАН — НИЖНЯЯ грань
  (`grantsGold: 1`). Цепочку нельзя строить на 3.5 золота — сумме, которой
  у игрока не бывает никогда, — иначе вернётся симптом part24 «откроется
  покупка X», а покупка не открывается. Оценка нижняя и по курсу: на ходу
  13 part39 верхняя покупка стоила 20.5 за три золота, то есть 6.8 очка
  за золотой вместо трёх; двигать `goldPointValue` под один случай нельзя.
  Цены спешки по образцу тёмного дара (part31) тут НЕТ намеренно:
  у дара заряды конечны и предложение растёт по ходам, а тут кулдаун
  равен броску, и скорость одна при любой грани — приберегать нечего.
  ПОРЯДОК шага решён отдельным решением игрока (04.09) — см. пункт
  «Шаг, ДОБАВЛЯЮЩИЙ золото, пробуется началом цепочки».
- **Открытие модального выбора обязано входить в ключ положения.** Раскопка
  открывается, не меняя ни золота, ни бордов, ни руки, — без выбора в ключе
  советник не пересчитывается, и оверлей показывает старые советы поверх
  модального экрана (part13, ход 5). Тот же урок, что с тринкетами в part9.
- **Дар и племена носителя магнита читаются с его карты.** `mechanics`
  минус MODULAR — что дарит (перерождение, щит…); `races` — к кому
  магнитится (рука-протез: к мехам И нежити). Бинарные ключевые слова
  второй раз не дарятся: носитель — крупнейший из тех, у кого дара ещё нет
  (part13, ход 19: перерождение советовалось уже перерождённому). Носитель
  называется и на неполном борде (ход 15). При виденном у соперников яде
  (по накопленным бордам — читаемый факт) носитель со щитом предпочтительнее
  крупного: яд убивает любым касанием, щит его поглощает, магнит со щитом
  в даре снимает угрозу сам. Указано игроком после part13.
- **Заклинание «Destroy a friendly X» целится в жертву, а не «на
  крупнейшего».** Жертва — наименьший свой племени X; без подходящей
  жертвы совет молчит. «Разделка туши» советовалась «на» голема 200/122 —
  уничтожить главную карту борда, к тому же не-нежить (part13, ход 21).
- **Статистика мест — открытые данные Firestone, не hsreplay.** hsreplay
  закрыт от выгрузки (403); Firestone публикует средние места героев
  и тринкетов открытыми JSON (`static.zerotoheroes.com/api/bgs/…`,
  срез last-patch / mmr-100), идентификаторы карт совпадают с нашими.
  Это ЧУЖИЕ агрегированные данные: в советах они всегда подписаны
  «по статистике», малые выборки (<500 партий) отфильтрованы, снапшот
  живёт в `data/bgstats/` и устаревает с патчем. Своих правил ценности
  героев нет и не выдумывается — статистика и есть их свёртка.
- **Выбор героя — тот же канал выборов с `ChoiceType=MULLIGAN`, отдельным
  полем `heroChoice`.** Сущность героя-заготовки при этом уже существует
  (part14) — экран выбора включается по самому выбору, не по отсутствию
  героя. Среди вариантов бывают скины (`_SKIN_A`) — статистика приводится
  к базовой карте.
- **Активация миньона — тег `HAS_ACTIVATE_POWER`, цена — живой тег
  `INTERACTABLE_OBJECT_COST` на нём же.** Цена сходится с плейсхолдером
  «Activate ({N})» → `TAG_SCRIPT_DATA_NUM`. Применение — блок PLAY
  на сущности, СТОЯЩЕЙ в PLAY: розыгрыш из руки отличается зоной (part14,
  Suspicious Prisonguard). Снимается ли доступность тегом после нажатия,
  в фикстурах не видно — «нажато в этом ходу» считается блоками, как
  у силы героя.
- **Заклинание-замена («Destroy a friendly X to get a random X») — свой
  распознанный эффект.** В тексте ни статов, ни золота, и разбор «только
  статы/золото/щит» возвращал null — заклинание наклейки Тюремщика молчало
  всю партию (part14). Цель — наименьший свой подходящего племени.
- **Боевой эффект «вашим \<племени\>» пуст без своих того племени.**
  «Rally: Your Undead have +1 Attack» на борде элементалей не делает
  ничего, а бонус дул ценность (part14, ход 21, Dustbone Devastator).
  Призывов это не касается: «Summon a Beast» приносит тело независимо
  от борда.
- **Скидка на покупку — тег `BACON_REDUCE_BUY_COST` на самом миньоне
  витрины.** part3: 9999 — миньоны даром (кламп в ноль), part4: 2 — цена 1
  у части витрины при трёх у остальных. Цена совета и «по карману ли»
  считаются через `buyCostOf` по каждому миньону отдельно. **С part35 это
  ЗАПАСНОЙ путь**: первым читается живой `COST` кнопки `DragBuy`
  (см. «Живая цена покупки лежит на КНОПКЕ» ниже) — тег скидки игра ставит
  не всегда.
- **Состав племён партии — по однoплеменным миньонам витрины, не по
  `CARDRACE`.** Строковый `CARDRACE` показывает одно племя даже
  у двуплеменной карты и создаёт фантомы: MECHANICAL и DRAGON в part11 —
  от «Руки-протеза» (MECH/UNDEAD) и Firescale Hoarder (DRAGON/NAGA),
  партий без мехов и драконов. Витрина предлагает только пул, поэтому
  однoплеменный миньон в ней доказывает племя; двуплеменные и амальгамы —
  нет. `seenShopCardIds` копится в step, а не в snapshot: живой и пакетный
  пути обязаны давать одно состояние.
- **Пара под тройку морозится только картой не ниже тира таверны.** Вторая
  копия — ставка на будущую тройку, а не тройка, и бонус копии сам же
  пробивал порог ценности: заморозка Buzzing Vermin 1/1 первого тира при
  таверне 2 (part15, ход 5). Третья копия собирает тройку немедленно
  и от тира не зависит. **Тот же порог тира — и у ветки ПЛЕМЕНИ** (part22,
  ход 5): снова Buzzing Vermin 1/1 при таверне 2, только держали его как
  «своего по племени» — на борде два зверя. Довод тот же: витрина второго
  тира предложит зверя не хуже. Племя тем и отличается от копии, что
  заменимо — конкретную третью копию ждут, а соплеменника нет.
- **Платная сила «даёт заклинание таверны» советуется как экономика.**
  «Get a random Tavern spell» за 1 (Холли'дэй, part15): ценность —
  примерно цена заклинания в витрине (два золота по курсу), очки за вычетом
  цены силы; сила за 2+ честно молчит. При остатке в 1 золото совет молчал,
  и золото сгорало.
- **Механика, названная словами в тексте, — синергия** (`perTextMechMate`,
  таблица `mechanicTextWords`: DEATHRATTLE, BACON_RALLY,
  BACON_SPELLCRAFT_ID, BATTLECRY). Titus Rivendare
  («Your Deathrattles trigger an extra time», AURA, без племени) на борде
  хрипов был слабейшим по статам и предлагался в продажу (part15, ход 17).
  Собственная механика синергией не считается («Deathrattle:» о себе).
  «Taunt» словами не разбирается: в текстах он описывает призываемых.
- **У заклинания без выбора цели цель не называется.** «Give a friendly
  minion of each type +2/+2» (Misplaced Tea Set, part15) раздаёт сама,
  а совет писал «→ на Deathstrider». Шаблоны `untargetedSpellWords`:
  of each type, random, left-/right-most, all friendly, your minions.
- **Провокация не вешается на миньона-«движка»** (AURA или текст-триггер
  «After/Whenever/At the start…», `engineTextWords`): она зовёт удары,
  а ценность движка — эффект. Slimy Shield советовался на Deathstrider —
  игрок не хочет его в приоритете ударов (part15, ход 19). Цель —
  крупнейший из остальных; борд целиком из движков возвращает крупнейшего.
- **Триггер О СЕБЕ («After this attacks…») движком НЕ считается**
  (`selfTriggerWords`, part17). Правило движка — про эффект от чужих
  действий, которому нужно, чтобы носитель дожил; собственный размен
  провокации не боится. Из семи миньонов пула с «After/Whenever this»
  четыре срабатывают от полученного урона, а один носит провокацию
  в своём же тексте. Прежнее чтение уводило Fortify с Wildfire Elemental
  8/3 на токен Water Droplet 3/3 (ход 11).
- **Усиление не вешается на кандидата в продажу, а кандидатов ДВА.** Бафф
  остаётся на миньоне навсегда. Первый кандидат — слабейший свой, которого
  правила сами назовут жертвой при первой покупке на полный борд (part17,
  ход 11: игрок сказал про цель «скорее всего продам»). Второй назван
  ТЕКСТОМ КАРТЫ: «When you sell this, …» (`sellValueWords`), и его продажу
  советник предлагает сам (`sellForGoldRule`, part18). На part36 (ход 7)
  план вешал «Allied Buckler +1/+3» на Sellemental 3/3 — крупнейшего
  на борде — и через два хода сам же советовал его продать; игрок повесил
  щит на Tusked Camper и Sellemental продал. Одно состояние, два правила,
  два несовместимых ответа — это и была дыра. Копия под тройку
  исключением не считается (её берут не телом), борд целиком
  из кандидатов возвращает выбор им же. Цель — крупнейший из ОСТАЛЬНЫХ.
- **Заморозка — отложенная покупка и судится правилами покупки.**
  На полном борде кандидат обязан перебивать жертву с запасом
  `sellMargin`, как в `buyRules` (копия и магнит слота не требуют).
  Порог от тира этого не ловит: к концу партии статы витрины растут
  вместе с бордом, и на part17 (ход 25) морозился Crackling Cyclone 38/43
  — 56 очков против порога 14 — при семи своих в 130–780 статов,
  слабейший из которых стоит 150.
- **Заклинание витрины, ДАЮЩЕЕ МИНЬОНА, — это покупка дешевле трёх.**
  «Steal a random minion from the Tavern» (Enchanted Lasso за 2, part17):
  ни статов, ни золота в тексте, и разбор возвращал `null` — заклинание
  было невидимо целиком. Шаблоны общие с силой героя (`givesMinionWords`:
  факт записан в ТЕКСТЕ, а не в том, кто его произносит), ценность — та же
  формула: средний миньон витрины плюс сэкономленное золото по курсу
  (у лассо среднее по витрине — точное ожидание, миньон берётся из неё же).
  Пока не по карману — держит витрину; на полном борде ветка молчит.
  Скидка засчитывается не всегда: у действия ПРЯМО СЕЙЧАС — только когда
  остатка хватает ещё на покупку (при трёх золотых и заклинании за два
  остаётся золотой, который сгорит, и «дешевле покупки» на деле означает
  «слабее покупки»); у заморозки — всегда, она и есть ставка на ход,
  где золота хватит на оба действия.
- **Ветви модального «Choose One» — отдельные карты снапшота `…t` и `…t2`.**
  `BG31_880` (Alliance Flag, «Choose One — Give a minion +{0}/+{1}; or
  +{2}/+{3}») — это `BG31_880t` (Allied Mace, «+{0}/+{1}») и `BG31_880t2`
  (Allied Buckler, «+{2}/+{3}»); плейсхолдеры у ветвей те же, что
  у родителя, и читаются из тегов сущности. Соглашение проверено на всех
  пяти модальных заклинаниях пула; порядок ветвей в тексте родителя
  с порядком карт НЕ совпадает (у Boundless Potential обратный), поэтому
  читается текст каждой ветви, а не позиция. Разбор по ветвям убрал и тихое
  завышение: сумма статов складывала обе ветви (+8 вместо +4) — тот же
  класс ошибки, что склеенный золотой текст (part19, ход 7).
- **При равной сумме статов «+3/+1 против +1/+3» брать ЗДОРОВЬЕ —
  порог взят 02.09 с третьего прогона.** 360 точек решения 32 партий
  билда, по 2000 симуляций на сторону, предрегистрация написана 17.08
  и с тех пор не менялась: среднее **−1.319 п.п. в пользу здоровья при
  пороге приёмки 1.158**. Прежние прогоны порога не брали и обещали
  ровно этот исход: 16 партий — −1.27 при 2.03, 23 партии — −1.530
  при 1.547 («запас сузился почти в ноль, перезапускать первым при росте
  выборки»). Взят порог не потому, что эффект вырос, — среднее даже
  уменьшилось, — а потому, что SE упала с 0.774 до 0.579. Поэтому
  `buffSplitPreference: 'health'`, и у равных по нашей шкале ветвей
  совет называет ту, где больше здоровья. **03.09 замер прогнан
  ЧЕТВЁРТЫЙ раз** — вынужденно: правка part36 меняет саму ЦЕЛЬ усиления
  (карта, чья ценность реализуется продажей, целью больше не бывает),
  то есть замер считает на других миньонах. 373 точки 33 партий,
  −1.357 при пороге 1.125, вердикт держится. Пятый прогон (34 партии) —
  −1.319 при 1.090, шестой (04.09, 35 партий) — −1.292 при пороге 1.058,
  СЕДЬМОЙ (04.09, 36 партий) — −1.256 при пороге 1.035 при SE 0.517,
  восьмой (05.09, 37 партий) — −1.247 при 1.008, ДЕВЯТЫЙ (05.09 ночью,
  38 партий, 429 точек) — **−1.377 при пороге 1.007**: впервые
  за несколько прогонов эффект не уменьшился, а вырос. **Оговорка
  обязательна: взглядов ДЕВЯТЬ, и номинальные 95%
  двух стандартных ошибок ослаблены сильнее прежнего (третий прогон
  стоял ближе к 88–90%).** Правило
  снимается одной строкой в `rules.ts`: если следующая выборка вернёт
  среднее внутрь порога — снимать, а не спорить. Перезапуск —
  `npm run spike:buff`.
- **Аура на ЧУЖИХ не назначается жертвой продажи, пока есть обычное тело.**
  Признак — механика `AURA` в снапшоте, кроме аур О СЕБЕ («Has +{0}/+{1}
  for each…»), у которых эффект и есть статы. В пуле 17 карт с AURA, слова
  «Has +» делят их начисто: восемь пумпят себя, девять усиливают чужое
  (Brann «Your Battlecries trigger twice», Titus, Drakkari Enchanter…).
  Наша шкала меряет ТЕЛА, и продавать по числу, про которое сами знаем,
  что оно не про эту карту, — ошибка, а не осторожность (part19, ход 27:
  Бранн 27/29 первым уходил в продажу при борде в сотни статов). Борд
  целиком из таких аур возвращает слабейшую из них — место откуда-то
  брать надо.
- **Миньоны бьют слева направо, и «Rally» срабатывает при атаке носителя.**
  Значит, риск не дожить до своего удара растёт к ПРАВОМУ краю борда,
  а не ко второму слоту (part19, ход 9: игрок опасался за Tusked Camper
  вторым номером). Перебор всех 24 расстановок подтвердил совет: 92.9%
  против 91.1% у лучшей расстановки с кампом первым и 90.0% у сыгранной.
- **В снапшоте к тексту части заклинаний приклеен ЗОЛОТОЙ вариант** —
  «…+{1} Health and Taunt.**3[x]**Give a minion +{0}/+{1} and Taunt.»
  (Fortify, part17). Числа обеих версий складывались: +3 здоровья читались
  как «+6 статов». Таких карт шесть, и все шесть — заклинания-усиления,
  то есть ровно те, чьи числа мы читаем. Режется в справочнике
  (`normalizeCardText`) по первому «цифры + `[x]`»; ведущий `[x]` —
  обычная разметка переносов и остаётся.
- **Платное обновление имеет смысл, только если найденное будет на что
  купить** (`paidRerollIsUseful`, part18 ход 7). После подъёма за 5 из 6
  остаётся золотой: витрину нового тира на него не купишь, а заморозить
  найденное значит отдать бесплатное обновление следующего хода. Прежний
  запрет раннего реролла был привязан к ДОСТУПНОМУ подъёму — и в плане,
  где подъём уже сделан, испарялся. С `lateRerollTier` правило снимается:
  там обновление — поиск карты под заморозку.
- **Синергия по механике считается в ОБЕ стороны** (part18, ход 17).
  Прямая: текст кандидата называет механику, свои её несут (Titus
  Rivendare на борде хрипов). Обратная: кандидат НЕСЁТ механику, а тексты
  своих её называют — нага со Spellcraft на борде, где Abyssal Bruiser
  считает «Tavern spells you've cast», а Fleeing Fugitive растёт от «cast
  a spell on this». Без обратной стороны советник вёл к демону на два тира
  выше, «который совсем не подходит композиции». Механика заклинаний —
  `BACON_SPELLCRAFT_ID`, таких текстов в пуле 97. Производитель, который
  сам же механику называет («Spellcraft: …»), в обратную сторону
  не считается.
- **Карта, чья ценность в ПРОДАЖЕ, продаётся, когда золото открывает ещё
  одну трату** (`sellForGoldRule`, `sellValueWords`, part18 ход 5). River
  Skipper обещает отдачу «when you sell this», и держать его ради этого
  слагаемого — не получить его никогда. Условие жёсткое: продажа обязана
  менять ЧИСЛО доступных покупок (пять золотых — один миньон, шесть — два),
  иначе она даёт монету, которой некуда деться. Удерживаемая ценность
  считается без слагаемого экономики; копия под тройку не продаётся.
  Это единственная продажа, которую план предлагает сам, — остальные живут
  внутри покупки (`sellFirst`).
- **Мусорная витрина — довод подняться, а не покупать и не крутить.**
  Правило из базы знаний JeefHS (docs/jeefhs.md), внесено по указанию
  игрока: когда лучший кандидат ниже порога «покупать нечего» (тот же
  порог, что у реролла), подъём получает очки выше слабых покупок —
  прежде подъём «по графику» имел ноль очков и проигрывал любому телу.
  Туда же: до `lateRerollTier` реролл молчит, пока подъём доступен
  и по карману; при недоступном подъёме (здоровье, тир, золото) реролл
  живёт — «золото иначе сгорит».
- **Предложения тринкетов открываются на ходах 11 и 17** (наша нумерация;
  6-й и 9-й ходы таверны) — замерено по всем двенадцати партиям билда
  248348, ходы в `rules.trinketOfferTurns`. Игра подбирает предложение
  под борд (тьюторинг, подтверждён игроком по базе JeefHS) — за ход
  до предложения советник напоминает держать 2+ миньонов желаемого
  племени (`trinketForecast`); амальгамы сигналом не считаются.
- **Тринкеты ранжируются «эффективным местом»: статистика минус
  0.3 места за своего миньона племени** (`trinketPlacePerTribeMinion`,
  курс — σ выборки снапшота). Правило JeefHS, подтверждено игроком:
  сильный нейтральный/экономический тринкет лучше слабого племенного;
  сильная синергия (4+ своих) статистикой не перебивается. Без
  статистики порядок прежний — свои племена первыми.
- **Карта, работающая ИЗ РУКИ, к розыгрышу не советуется.** Признак —
  собственный текст (`handWorkerWords`), и пород две: «Start of Combat:
  If this minion is in your hand, summon a copy of it» (Flighty Scout) —
  тел в бою поровну, копия приходит и без розыгрыша, а слот тратится
  НАВСЕГДА; «While this is in your hand… gain +{0}/+{1}» (Bream Counter,
  Timewarped Astrogill) — розыгрыш останавливает рост, и цена остановки
  ближайшему бою невидима, как у экономики. Купить такую по-прежнему
  советуется: из руки она и работает. В пуле 14 карт с «in your hand»,
  и ВСЕ мурлоки — трое работают из руки, одиннадцать её едят (Costume
  Enthusiast: «Gain the Attack of the highest-Attack minion in your
  hand»). Замер (`npm run spike:hand`) правило НЕ доказывает: он объявлен
  негодным по собственному критерию — контроль порога не взял ни разу
  из трёх (0.648 при 1.170, 0.546 при 0.937, **0.332 при 0.674** на 32
  партиях 02.09), потому что лишнее тело ближайший бой чаще всего
  не меняет вовсе (из 118 точек контроля разошлись 16). Рост выборки
  этому замеру не помогает, и это уже видно: среднее падает ВМЕСТЕ
  с порогом — новые точки не приносят сигнала, а размывают его (у
  `spike:buff` было наоборот, и он порог в итоге взял). Согласие
  прогон показал: у «играет из руки» разность розыгрыша осталась нулём
  (−0.05) при +0.33 у обычной карты (part22, ходы 5 и 17).
- **Порог тройки — НЕ константа: его меняет сила героя** (part7, 26.08).
  `Double Time` (`BG34_HERO_002p`) обещает «You only need 2 copies to make
  minions Golden», и лог это подтверждает: все три золотых той партии
  собрались при ДВУХ простых копиях, при контроле в три на обычных героях
  (part17, part19). Число читается из текста силы (`tripleCopies`,
  `tripleCopiesWords`, `copiesForTriple`), а ценность копий считается
  по РАССТОЯНИЮ до тройки: последний вес таблицы `copiesBonus` достаётся
  тому, кого покупка делает золотым. При обычных трёх копиях выходят ровно
  прежние числа. Пока порог был константой, двенадцать очков «собирает
  тройку» стояли на второй копии — на ход позже, чем надо, — и целую
  партию советник недооценивал первую. Сравнений `copiesOwned >= 2`
  по местам больше нет: их было семь, и разъехались бы они молча.
- **Сила, дающая статы за РОЗЫГРЫШ, считается — и ровно один раз**
  (part27, 26.08). `Hat Trick` (`TB_BaconShop_HP_042`): «When you play
  a minion, give it a +1/+1 hat that passes to a friendly minion when
  sold». Число читаемое, шкала наша (`perStatPoint`), своего веса
  у слагаемого нет намеренно. Прибавляется на стороне ПРИОБРЕТЕНИЯ,
  а у своего миньона вычитается (`ownValue`, `sellForGoldRule`): шляпа —
  настоящий энчант, её +1/+1 уже сидят в `attack`/`health`, и второе
  слагаемое было бы той же шляпой, посчитанной дважды. Слагаемое ОДИНАКОВО
  у всех кандидатов, поэтому порядок покупок оно не меняет — меняет
  покупку против обновления и розыгрыш против «ничего». Цикл
  «купить-разыграть-продать» ради шляпы (при продаже она переходит
  на другого) НЕ считается: это правило про лишнее золото на полном борде,
  и вносить его надо с замером — именно его игрок крутил в part27 сотню
  раз (69 покупок, 98 продаж, 199 розыгрышей).
- **Сила героя — такой же читаемый текст, как текст миньона борда.**
  Прежде ценность покупки смотрела только на борд и на саму карту, и герой
  не влиял ни на что, хотя лежит в состоянии с part13. У Флургла сила
  «Рыбалка» («After you sell 5 minions, get a random Murloc») называет
  и ПРОДАЖУ, и ПЛЕМЯ, а советник предлагал дракона вместо River Skipper
  («When you sell this, get a random Tier 1 minion») — карты, чьё обещание
  реализуется ровно тем действием, которое сила вознаграждает (part22,
  ход 1). Слагаемых два, оба ОДНОКРАТНЫЕ (факт о кандидате, а не о числе
  своих): племя из силы — весом `perTextTribeMate`, продажа — весом
  `economy`. **Размер этого механизма пересчитан 26.08 и оказался куда
  меньше, чем здесь стояло:** в пуле Battlegrounds племя называют
  **24 силы из 174**, продажу — **три**. Прежние «140» были посчитаны
  по всем 2147 картам типа HERO_POWER снапшота, то есть по всему
  Hearthstone вместе с Дуэлями и Наёмниками, — фильтра пула в том счёте
  не было. Читать запись надо так: слагаемые верны, но покрывают восьмую
  часть пула, а не большинство сил. Все числа покрытия закреплены тестом
  (`test/advisors/tavern/heroPowers.test.ts`) — в прозе они разъезжаются
  и от патча, и от наших же правок.
- **Удвоитель механики на борде — множитель, а не рядовая связь.** В пуле
  их ровно ТРОЕ, и они делят три механики: Бранн Бронзобород (кличи),
  Titus Rivendare (хрипы), Drakkari Enchanter (конец хода); все трое —
  AURA. `perTextMechMate` считал Бранна за полторы очка, а при нём
  «Battlecry and Deathrattle: Get a Deepwater Clan» приносит ДВЕ карты
  (part22, ход 23: кличевой мурлок стоял вторым после эффекта конца хода,
  удваивать который некому). Очки начисляются ТОЛЬКО там, где известно
  что удваивается: у триггера, приносящего карту, курс уже есть — тот же
  `heroPowerSpellValue`, что у прокрутки генератора. Удвоение эффекта
  без добычи остаётся обычной связью: множитель реален, а цены у него нет.
- **Заклинание, крадущее ИЗ ВИТРИНЫ, оценивается по ОСТАТКУ витрины.**
  «Steal a random minion from the Tavern» (Enchanted Lasso) берёт из той
  же витрины, которую мы оцениваем, а к моменту применения лучшие карты
  будут куплены нами. Среднее по ВСЕЙ витрине считало лучшую карту дважды
  — и «мы её купим», и «лассо может её дать» (part22, ход 7). Признак
  «из витрины» (`givesMinionFromShopWords`) отличается от «даёт миньона»:
  «Get a random Tier 1 minion» берёт из пула, и витрина там ни при чём.
- **Шаг, после которого золото СГОРАЕТ, соревнуется не сам с собой,
  а с цепочкой** (part23, ход 5). Жадный план берёт верхний совет и живёт
  остатком; верхний совет умеет ЗАПЕРЕТЬ остаток — оставить золото,
  которого не хватает ни на что. Пять золота: тёмный дар за 3 (8.0 очков)
  и два сгоревших против прокрутки за чистых 2 (7.5), оставлявшей ровно
  три на покупку (7.0). Разрыв первого шага — полбалла, цена запертого
  остатка — шесть очков по курсу `goldPointValue`. Поэтому при сгорании
  план пробует начать с ближайших соперников верхнего совета и берёт
  цепочку с бо́льшим «сумма очков минус сгоревшее золото». Полного
  перебора корзин это не вводит: развилка ОДНА, на первом шаге, и только
  после признания, что золото сгорает. Порядок самих советов правка
  не трогает — список ранжирует ОТДЕЛЬНЫЕ действия.
- **ПОДЪЁМ ТАВЕРНЫ входит в развилку плана — решение игрока 17.08
  (part25).** Жалоба на «подъём за 5 из 6 с горящей монетой» пришла
  третий раз подряд (part23 ход 5, part24 ход 7, part25 ход 7), и две
  правки по ней были написаны и откачены. Вопрос вынесен игроку
  с числами: подъём — верхний совет на 4-м ходу таверны в 21 партии
  из 22 (`npm run spike:level`), а по датасету 25 партий он на этом ходу
  ВСЕГДА тир 2 и берёт тир 3 на 5-м (8 партий) или 6-м (17). Выбран
  вариант «пусть план сравнивает подъём с цепочкой». Прежнее возражение
  снято ЯВНО, а не спрятано: у подъёма появилось поле `standaloneScore`
  — своя ценность, то есть одна срочность, без лучшей покупки внутри;
  в очках СПИСКА лучшая покупка стоит ради места над покупками,
  а в цепочке она делается по-настоящему отдельным шагом, и считать её
  дважды нельзя. Две границы: альтернатива — это ход БЕЗ подъёма ЦЕЛИКОМ
  (иначе после вынужденного первого шага подъём возвращается вторым,
  part24 ход 7), и **мусорная витрина подъём в развилку не отдаёт**
  (`standaloneScore` там не заполняется: довод ветки JeefHS — «покупать
  нечего», и цепочка из тех же покупок ему не возражение). Следствие
  названо игроку заранее и принято: на шести золотых цепочка почти всегда
  перевешивает один тир, и канонический подъём part20 (ход 7) исчезает.
- **Шаг, ДОБАВЛЯЮЩИЙ золото, пробуется началом цепочки всегда и выигрывает
  НИЧЬЮ — решение игрока 04.09 (part39).** Своих очков у нажатия силы-кубика
  мало (7.5 против 20.5 у верхней покупки), в тройку ближайших соперников
  (`maxAlternativeStarts`) оно не попадало, и жадная цепочка ставила его
  ПОСЛЕ покупок — туда, где принесённое золото уже некуда девать; игрок все
  три раза за партию жал силу ПЕРВЫМ действием хода. **Одного впуска
  в развилку оказалось МАЛО, и это проверено прогоном, а не выведено:**
  в план такой шаг отдаёт НИЖНЮЮ грань (`grantsGold: 1` при цене 1), поэтому
  цепочка из тех же шагов в другом порядке стоит РОВНО СТОЛЬКО ЖЕ, и строгое
  сравнение (part25) оставляло нажатие в хвосте навсегда. Отсюда вторая
  половина правки — тай-брейк, и причина у него арифметическая: между двумя
  одинаковыми по нашей шкале цепочками выбирать надо ту, где неизвестное
  число становится известным РАНЬШЕ, потому что всё, что стоит после
  нажатия, посчитано на заниженном золоте, и игрок пересчитает это сам,
  увидев бросок. Обратное (нажать последним) не даёт взамен ничего.
  Исключение узкое: тай-брейк работает ТОЛЬКО когда первый шаг альтернативы
  сам приносит золото; в остальном строгое превосходство сохранено, чтобы
  порядок советов и план не расходились без причины.
- **Тир, НАЗВАННЫЙ в тексте «даёт миньона», читается — витрина ему
  не мерка** (part23, ход 11). «Get a random Tier 1 minion» (Recruit
  a Trainee за 2) на третьем тире оценивался средним по витрине третьего
  тира — 11.5 очков за тело первого. Тир пишется двумя способами, оба
  из текста: числом (`Tier N`) и словами «своего тира» (`of your Tier` —
  Search Through Time, Boundless Potential); таких заклинаний в пуле 21.
  Ожидание считается ПУЛОМ того тира (`cards.poolOfTier`), той же шкалой
  и на том же борде: свои по племени, ключевые слова и копии у пришедшего
  миньона будут настоящие, и усреднение по пулу — их честное ожидание,
  а не поправочный коэффициент. Тир, не названный вовсе («of your most
  common type»), по-прежнему меряется витриной — она и есть выборка
  своего тира. Жалоба игрока дословно: «это работает для ранней игры».
- **Наценка считается тем же курсом, что скидка.** Прежнее
  `Math.max(0, minionCost − cost)` делало разницу односторонней:
  заклинание дешевле покупки получало прибавку, а ДОРОЖЕ покупки
  не платило ничего. Это не осторожность, а ошибка знака — золото давно
  переведено в очки, и курс обязан работать в обе стороны (part23,
  ход 15: Planar Telescope за 4 стоил 11.3 очка вместо 8.3).
- **Заморозка ради заклинания судится ЦЕНОЙ, и спор об этой ветке
  закрыт 17.08 (part23) — правило part19 ОТМЕНЕНО.** Два условия, оба
  структурные. Первое: витрину держат ради заклинания, только если оно
  ДЕШЕВЛЕ покупки — в этом весь смысл ветки (part17, ход 1: тело за два
  золота там, где покупка стоит три). Заклинание дороже покупки такой
  ставкой не является: то же тело в тот же ход просто покупается,
  и дешевле (Planar Telescope за 4). Второе: планка = «свежая карта
  своего тира» ПЛЮС цена самой заморозки, и оба слагаемых — ценности
  карты, посчитанные одной функцией на одном борде (пул своего тира
  через `cards.poolOfTier` против среднего по доживающей витрине).
  Прежняя планка была маржинальной (`threshold − bestKept`) и сравнивала
  ЧИСЛА С РАЗНОЙ НАЧИНКОЙ: голое `2×тир+4` против полной ценности карты
  на борде. На собранном борде разность падала в ноль (part23, ход 15:
  13.0 против 14 — порог ЕДИНИЦА), и витрину держало любое заклинание,
  дающее миньона. Новая планка растёт с тиром сама: лассо берёт её
  на первом тире (5.3/4.3 → 6.4 при лассо 7.0) и не берёт со второго
  (7.6/5.0 → 10.3 при 8.0). Это дословно то, что игрок сформулировал
  в part23: «работает для ранней игры». Тем самым разрешено расхождение
  part19 («совет исчез после подъёма» — просил вернуть) против part22
  («практического эффекта не вижу» — просил убрать): обе жалобы были
  про одну карту на одном тире, и правильный ответ оказался не про
  подъём, а про цену. Тесты part19 и part22 переписаны, а не удалены —
  они держат новое поведение и хранят историю спора.
- **Тёмный дар — это РАСКОПКА ЧУЖОГО ТЕЛА с даром, а не усиление

  `floor((золото следующего хода − цена предложения) / 3)`; дешевле

  о заморозке ради заклинания (part17 → part19 → part22 → part23 → part24):

  свежая карта дороже тела первого тира (part23 ход 11: 10.70 против 9.02
  — молчит). «Работает для ранней игры» стало следствием
  размера витрины, а не порогом по тиру. Оговорка: свежая сторона —

  эффект текста) — выстреленный миньон живёт ОДИН размен, и тир, племя,
  копии, экономика к нему не относятся; СТРЕЛЯЕМ тем, чего не купим —
  карта уходит из витрины насовсем, поэтому отбрасываются `affordable`
  лучших по обычной ценности, где `affordable` ограничено и золотом,
  и свободными слотами борда; БЕЗ СВОБОДНОГО СЛОТА совет молчит — это
  сказано в самом тексте силы. В пуле такая сила ОДНА: слова «remove
  a minion» среди 2147 карт типа `HERO_POWER` есть только у неё. Заморозку
  выстрел не бережёт (в part29 игрок сам стрелял по замороженной витрине),
  и запрета на это нет намеренно.
- **Заморозка ради «предложения дешевле покупки» обязана проверять
  СОБСТВЕННОЕ обещание — «два тела вместо одного»** (part29, ходы 5 и 7).
  Витрину держат ради заклинания, дающего миньона (part17), или продажного
  генератора (part25) ровно потому, что предложение стоит меньше трёх
  и занимает золото, которое иначе сгорит. Но сгорает оно не всегда: тел
  без предложения `⌊золото / 3⌋`, с предложением `1 + ⌊(золото − цена)
  / 3⌋`, и золото берётся ТОГО хода, который называет сам совет
  (`turnAffordingBoth` — на первом ходу таверны это третий). Пять золота —
  лишнее тело есть, шесть и семь — нет, восемь — снова есть. Дословно так
  и сказал игрок: «5 золота скорее всего последнее выгодное значение для
  его заморозки, дальше я уже смогу покупать два существа за 6 золота
  и существо + улучшение таверны за 7». Проверка общая для обеих веток —
  вопрос у них один. Планку `spellThresholdOf` (part27) и пороги по тиру
  правка не трогает: это дополнительное необходимое условие, а не новая
  шкала. Тем же счётом снялась заморозка ради River Skipper на part22
  (ход 7) — та, про которую игрок сказал «не вижу практического эффекта»
  и которая была записана первым кандидатом на снятие.
- **Цена бывает НЕ в золоте, и читается это тегом

  «не по карману» при нуле и «даёт 1, а стоит 3» при деньгах. Тег ставит
  игра, и не только на карты со своей ценой в здоровье: Malchezaar
  `BG26_524` и Bazaar Dealer `BG28_905` на борде, наклейки

  золото» у нас нет и выдумывать его мы не станем**, поэтому ветка живёт
  ровно там, где курс не нужен: при миньоне «After your hero takes damage,
  rewind it» на борде (`healthRewindWords`, четыре карты пула — Soul
  Rewinder тира 2, Timewarped Rewinder тира 3, Ashen Corruptor
  и Timewarped Archimonde тира 5). Что триггер срабатывает именно на трату
  здоровья, показывает лог: `META_DATA Meta=SPEND_HEALTH Data=3`, броня
  героя 14 → 11 и тут же обратно 14. Без такого миньона совет молчит.
  На МИНЬОНАХ тот же тег тоже бывает, и там цена по-прежнему считается
  золотом — фикстуры нет, вслепую не вносим.
- **Копии под тройку игра считает и В РУКЕ, значит розыгрыш ставки её
  не улучшает** (part29, ход 19). Тег `BACON_PAIR_CANDIDATE` игра ставит
  на карту витрины и тогда, когда единственная наша копия лежит в руке:
  проверено прогоном по двум фикстурам — семь таких случаев (part29 ход 23
  `BG31_330`, part22 шесть штук), и ни одного «пара без копии». Отсюда две
  правки. Первая: бонус за копию — ценность ВЛАДЕНИЯ, и в очках розыгрыша
  он стоял вторым разом, да ещё и ПРИЧИНОЙ («вторая копия» в обосновании
  того, чтобы карту выставить). Вторая: ставка, занимающая ПОСЛЕДНИЙ
  свободный слот, разменивается на один бой — следующая покупка встретит
  полный борд продажей, и продана будет именно ставка, потому что копию
  под тройку берут не телом. Поэтому розыгрыш такой карты советуется,
  только когда её тело в бою (`combatValue`) стоит дороже ставки
  (`copiesBonus`); при равенстве ставка остаётся в руке — розыгрыш
  необратим, а рука не стоит ничего. Тройки это не касается: её собирают
  немедленно.
- **Сила «Discover a \<Tribe\>» — «даёт миньона», и Discover — это
  ВЫБОР** (part30, ход 1). Племя без слова «minion» читается той же
  `tribeMinionRace`, что выбор сил (part26) и ветви модальных миньонов
  (part28), — в общий `givesMinionWords` оно по-прежнему не вносится

  племени тиров 1..своего, и у Discover оно НЕ среднее: три карты
  предложены, берётся одна, и считается ожидание лучшего из трёх
  порядковой статистикой (C(i−1,2)/C(n,3)) на той же шкале. Это
  арифметика, а не надбавка: средний мех тира 1 стоит 6.25 и проигрывает
  покупке 7.0, а выбор из Lullabot 5.0 и Cord Puller 7.5 — это 7.5,
  и игрок взял ровно Cord Puller. «Get a random \<Tribe\>» остаётся

- **Статы «minions in the Tavern» ложатся на ВИТРИНУ, а не на наш борд**

  нижняя: заморозка могла бы сохранить усиленных, покупки считаются

- **«Gain N Gold next turn» — золото ОТЛОЖЕННОЕ, и с живым оно
  не складывается** (part30, ход 9). Тот же урок, что предел золота

- **Сгорающее золото уходит в обновление-СТОК — только под триггер трат
  на борде** (part30, ход 19). Условия переборные, не пороговые: золоту

- **Кровавые самоцветы молчат КОДОМ, а не удачей нулевых плейсхолдеров**

- **У заряда тёмного дара есть ЦЕНА — тело, которое он принёс бы позже**
  (part31). Зарядов три на партию (кнопка создаётся с `NUM_2=3`, живое
  число — `darkGiftCharges`), предложение растёт по ходам таверны
  до десятого (таблица part24) и дальше плоское. Пока дар мерился одним
  телом «сейчас», он стоял верхней строкой с первого хода, где по карману
  (part31: с хода 7; на скриншоте 14.4 против покупки 14.0), а игрок все
  три заряда нажал на 10–12-м ходах таверны. Правило без нового веса:
  ходов впереди — `remainingTurns` (замер part28), и если их с нынешним
  больше, чем зарядов, нажатие сейчас вытесняет самый ранний из последних
  ходов — `сейчас + (впереди + 1 − зарядов)`; цена спешки — разница тел
  того хода и этого (`averagePoolValue` по тирам таблицы, дробный ход —
  линейно). С десятого хода цена ноль, и совет говорит «сильнее
  предложение уже не станет — жать». Оговорки записаны в правиле:
  темповая цена тела (сейчас воюет больше боёв) не считается, горизонт
  без здоровья (part28). Причина обязана печатать и горизонт, и цену.
- **Миньон, приходящий В РУКУ, на полном борде вычитает жертву — везде,

- **Сила героя, дающая СВОЕМУ миньону ключевое слово, советуется
  и называет цель** (part32, Король-лич, «Give a minion Reborn until next
  turn»). Слово — группа шаблона `heroPowerKeywordWords`, сведённая
  к живому признаку миньона таблицей `BINARY_KEYWORDS`; ценность —
  того же слова на цели теми же весами и капами, что у покупки
  (`keywordValue` — одна функция на `minionValue` и на дар), минус цена

  хрип, сам дарящий перерождение (цепочка, пока есть кому получить),

  крупнейшее тело, провокация обходит движков. План применяет шаг
  по-настоящему (`grantsKeyword` → слово на цели гипотетического борда).
  В пуле активных сил с таким текстом две (Reborn Rites, Boon of Light);
  пассивный «Start of Combat: Give your left-most minion…» шаблон
  не ловит намеренно.
- **Шаблон «summon» терпит перенос строки — третий случай урока part16.**

  по тексту снапшота пишет `\s`, а не пробел, — и проверять это надо
  на карте с переносом, а не на удобной строке.
- **Сила «after you buy N <механика> minions, get a <карта>» читается,
  и доля награды считается ПО ОСТАТКУ счётчика** (part34, «Бранное дело»:
  «After you buy 4 Battlecry minions, get a Brann Bronzebeard»). Игрок

- **Золото — `RESOURCES` + `TEMP_RESOURCES` − `RESOURCES_USED`, и третий
  тег не факультативен** (part34). `TEMP_RESOURCES` — временное золото
  хода: «Gain 1 Gold next turn» (Southsea Busker), «Gain 2 Gold next turn»
  (Careful Investment — в part30 доходит до 6) и ВОЗВРАТ ЗА ПРОДАЖУ, пока
  в ходу ничего не потрачено (`RESOURCES_USED` ниже нуля не опускается).

  как ничего не давшая; тег с ненулевым значением есть в 29 фикстурах.
  Семантика — как в игре: `gold` включает временное (числитель «11/10»),
  `goldTotal` остаётся базовым максимумом (знаменатель), потраченная
  временная часть входит в `goldSpent` — точки решения (`turns.ts`)
  и датасет читают «потрачено ли что-то», и покупка целиком из временного
  золота обязана считаться тратой; план (`spend.ts`) ведёт `goldSpent`
  приращением остатка, а не разностью `goldTotal − gold`. Границы хода
  с ненулевым остатком в фикстурах не встретилось ни разу — сброс доверен
  тегам игры, а не нашему счётчику.

  числа прежние. Где цена по правилу ОСТАЛАСЬ и почему: витрина
  будущего хода (`turnAffordingBoth`, `purchasesAfter`, планка заморозки)
  — цен ещё не существует; «заклинание дешевле покупки» — там цена
  покупки работает ШКАЛОЙ, а не кошельком. И отдельно: ПУСТАЯ витрина
  отвечает по правилу игры, потому что «цен не видно» — это не «купить
  не на что»; на этом упал тест подъёма, и различие пришлось назвать
  вслух.
- **Заклинание, которое ОБНОВЛЯЕТ витрину и назначает ей цену, советуется
  ТЕЛАМИ** (part35, «Refresh the Tavern with Battlecry minions. They cost
  (1)» — чародейство тринкета в руке, бесплатно каждый ход). Ни статов,
  ни золота, ни миньона в тексте — `spellEffect` возвращал `null`,
  и заклинание было невидимо целиком: на скриншоте при двух золотых
  «ОБНОВИТЬ за 1» и «НИЧЕГО». Правило (`discountRefreshRule`,
  `discountRefreshWords` — группа шаблона это цена; механика наполнения —
  той же таблицей `mechanicTextWords`) считает без нового веса: покупок
  по новой цене на остаток золота (не больше размера витрины тира)
  по ожиданию пула названной механики тиров 1..своего
  (`averagePoolValue` с фильтром по механике; кличевых в пуле 46 из 396)
  минус покупки нынешней витрины по карману (лучшие по ценности, пока
  хватает золота). Вычет и делает совет честным против покупки: при
  десяти золотых и двух драконах по 30 в списке заклинание молчит,
  а в плане встаёт после подъёма за 8 — «на остаток 2 два тела», дословно
  ход игрока. В плане шаг обрывает цепочку, как обновление кнопкой
  (`refreshesShop`), и забирает золото обещанных покупок (`refreshSpend`):
  иначе остаток числился сгоревшим, и развилка ставила заклинание туда,
  где остаток меньше. Ожидание — среднее по пулу, а не лучшее-из-N
  (нижняя оценка, как у «Get a random X»); в снапшоте карта с таким
  текстом одна.

## Настройка логирования — обязательна, иначе данных не будет

Два файла в **разных** местах, это легко перепутать:

**`%LOCALAPPDATA%\Blizzard\Hearthstone\log.config`** — что логировать:

```ini
[Power]
FilePrinting=true
Verbose=true
```

**`<каталог установки игры>\client.config`** — предел размера лога:

```ini
[Log]
FileSizeLimit.Int=1000000
```

Без второго клиент обрывает **всё** файловое логирование на 10 000 КБ и больше
не возобновляет: полная партия BG весит ~40 МБ и не влезает. Настройка читается
один раз при старте клиента. Файл лежит рядом с игрой, поэтому обновление
Hearthstone может его снести — `ensureLogSizeLimit` проверяет и чинит.

## Что известно про формат Power.log

**Полная фактура — в [docs/power-log.md](docs/power-log.md).** Там всё с
доказательствами из фикстур: числа, цитаты строк, что проверено человеком,
что скриншотом, а что остаётся гипотезой. При работе с парсером читать оттуда,
а не вспоминать.

Ниже только то, на чём ломаются чаще всего. Каждый пункт стоил отдельного бага,
и все они дают **не падение, а тихо неверный результат**:

1. **UTF-8 без BOM, переводы строк смешанные.** Обычные строки CRLF, баннер
   обрезки — одиночные LF. Разбивать по `/\r?\n/`.
2. **`entityName` может содержать вложенные скобки** —
   `[entityName=UNKNOWN ENTITY [cardType=INVALID] id=255 …]`, около 10% всех
   дескрипторов. Разбирать позиционно по именам полей, не по закрывающей скобке.
3. **Канал-источник — `GameState.DebugPrintPower`.** `PowerTaskList` дублирует
   его событие в событие; применять оба — применить теги дважды.
4. **`BLOCK_END` есть не у каждого `BLOCK_START`.** Вложенность считать
   по отступу, а не по парности.
5. **Дескриптор в `TAG_CHANGE` показывает состояние ДО изменения.** Зону
   и позицию брать только из явных тегов, иначе мёртвые миньоны воскресают.
6. **`HIDE_ENTITY` несёт смену зоны и начинается не с `TAG_CHANGE`.**
   Там же: **`SHOW_ENTITY` называет сущность через `Entity=`, а `FULL_ENTITY`
   через `ID=`** — разбор, знающий одну форму, теряет 1349 раскрытий карт
   за партию и оставляет их без `cardId`.
7. **Отбирать сущности белым списком** (`CARDTYPE=MINION`), а не «всё кроме».
8. **Одинаковые теги приходят на разные сущности с разным смыслом.** `TURN`
   на `GameEntity` — ход партии, на игроке — его счётчик, вдвое меньше.
9. **Своего игрока определять по ненулевому `GameAccountId`**, не по номеру:
   `PlayerID` меняется между партиями (в фикстурах 4 и 3 у одного человека).
10. **Золото — это `RESOURCES` плюс `TEMP_RESOURCES` минус
    `RESOURCES_USED`.** Прямого тега на остаток нет. `TEMP_RESOURCES` —
    временное золото хода («Gain N Gold next turn», возврат за продажу при
    нуле потраченного), тратится первым; без него ход после Southsea
    Busker читался на монету беднее (part34).
11. **Следующий противник известен заранее** — тег `NEXT_OPPONENT_PLAYER_ID`
    в таверне, проверено 18 совпадений из 18. Кто именно скрыт за чужим слотом,
    определяется через тег `PLAYER_ID` его героя, а не по подписи слота:
    та в поздних боях остаётся «Бармен Боб». Тег
    `BACON_CURRENT_COMBAT_PLAYER_ID` — это НЕ противник, а сам игрок.
12. **Борд противника снимать в начале боя**, по первому блоку `ATTACK`:
    к выходу в таверну его миньоны уже убраны из `PLAY`.

## Как размечать новые фикстуры

Видео бесполезно — ассистент его не читает. Работает так:

1. Игрок делает 4–6 **скриншотов** в конце фазы таверны, на разных ходах.
2. Кладёт в `data/screenshots/` (в git не коммитятся, см. `.gitignore`).
3. Ассистент прогоняет `npm run demo:phase1` на логе и сверяет сам.
4. Совпавшее идёт в `partN.expected.json` с пометкой `verifiedBy: скриншот`.

Скриншоты снимаются в середине фазы, а демо печатает её конец — расхождение
в единицу здоровья это норма, а не баг. Проверять то, что от момента не зависит:
состав, порядок, атаку, золото, тир.

Пометки в `expected.json` различаются по силе: `подтверждено человеком` —
игрок видел это своими глазами в игре; `скриншот` — сверено по картинке.
