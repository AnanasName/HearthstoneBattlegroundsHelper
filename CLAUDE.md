# HS Battlegrounds Assistant — ТЗ проекта

## Цель

Десктопный помощник для Hearthstone Battlegrounds, который в реальном времени читает состояние партии из лог-файлов игры и подсказывает наилучшие ходы: оптимальную расстановку миньонов, шансы на исход боя, решения по покупкам и левелингу таверны.

**Никакого компьютерного зрения.** Источник данных — только `Power.log`, который Hearthstone пишет при включённом `log.config`. Никакого чтения памяти процесса, никакой автоматизации ввода (это бан). Оверлей только показывает информацию, все действия в игре выполняет человек.

**Цель — промышленное ПО, а не личная утилита.** Это уже повлияло на решения
и должно влиять дальше: от пользователя нельзя требовать ручных действий вроде
переподключений посреди партии, установка сводится к двум конфигам от инсталлятора,
а приложение само проверяет и чинит настройки при каждом запуске (обновление
Hearthstone может снести `client.config`, он лежит в каталоге игры).

## Стек

- **Язык:** TypeScript (strict mode), Node.js 20+
- **Симулятор боя:** пакет `@firestone-hs/simulate-bgs-battle` (репозиторий `Zero-to-Heroes/api-simulate-battlegrounds-battle`) — не писать свой симулятор, интегрировать готовый
- **Тесты:** Vitest
- **UI (поздние фазы):** Electron, прозрачное always-on-top окно
- **Данные карт:** JSON из HearthstoneJSON (https://hearthstonejson.com), файл `cards.collectible.json` + battlegrounds-теги; закоммитить снапшот в `data/`, не тянуть в рантайме

## Архитектура

```
Power.log → [Watcher] → [Parser] → GameState → [Advisors] → [Overlay/CLI]
                                        │
                          ┌─────────────┼─────────────┐
                     BattleAdvisor  PositionAdvisor  TavernAdvisor
                     (Монте-Карло)  (перебор 7!)     (эвристики)
```

Модули независимы, общаются только через типизированный `GameState`. Каждый модуль — отдельная директория в `src/` со своими тестами.

## Фазы разработки

Работать строго по фазам. Не начинать следующую, пока не выполнен Definition of Done текущей.

### Фаза 1 — Parser + GameState (ядро проекта)

Парсер `Power.log`: tail файла, разбор строк `GameState.DebugPrintPower`, `PowerTaskList`, тегов `TAG_CHANGE` / `FULL_ENTITY` / `SHOW_ENTITY`, сборка `GameState`.

`GameState` минимально содержит:
- фаза партии (выбор героя / таверна / бой / конец)
- номер хода, тир таверны, золото
- свой борд: миньоны с cardId, atk/hp, taunt/divine shield/poisonous/reborn/windfury, golden, enchantments, порядок слева направо
- своя рука и герой (hp + armor, hero power)
- последний увиденный борд каждого оппонента + его hp/tier
- следующий оппонент, если известен

**DoD фазы 1:** для каждой fixture-партии из `data/fixtures/` есть тест, который прогоняет лог целиком и сверяет `GameState` в контрольных точках (заранее размеченных вручную) — состав борда, золото, тир, hp. Все тесты зелёные.

### Фаза 2 — BattleAdvisor

Интеграция `@firestone-hs/simulate-bgs-battle`: маппинг нашего `GameState` во входной формат симулятора, прогон N симуляций (N настраиваемый, старт — 3000), вывод win/tie/loss % и вероятности летала в обе стороны.

**DoD:** на fixture-боях с известным фактическим исходом симулятор выдаёт распределение, где фактический исход не является выбросом; время прогона 3000 симуляций ≤ 2 с на обычном железе.

### Фаза 3 — PositionAdvisor

Перебор перестановок своего борда (≤ 7! = 5040), каждую прогонять сокращённым числом симуляций (например 300), лучшие кандидаты — полным. Выдавать топ-3 расстановки с их win %.

**DoD:** на fixture-состоянии с заведомо важной позицией (клив, poisonous, taunt) советник находит расстановку не хуже той, что была сыграна фактически. Полный перебор укладывается в ≤ 10 с; если нет — beam search.

### Фаза 4 — TavernAdvisor (эвристики, без ML)

Правила: когда левелить (стандартные тайминги по золоту/хп), что покупать (синергия с текущим бордом по племенам и ключевым парам карт), когда реролл. Конфигурация правил — данными (JSON/TS-таблицы), не хардкодом в логике.

**DoD:** unit-тесты на каждое правило + сквозной тест «состояние → рекомендация» на fixture-состояниях.

### Фаза 5 — Overlay

Electron: прозрачное окно поверх игры, показывает вывод советников. До этого — CLI-режим (`npm run watch`), который печатает советы в терминал; CLI остаётся навсегда как режим отладки.

### Фаза 6 (опционально, отдельное ТЗ) — ML

Предсказание финального места по `GameState` на ходу N. Только после того, как фазы 1–5 стабильны и накоплен датасет собственных партий. В этом ТЗ не детализируется.

## Правила работы с логами — критично

1. **Не выдумывать формат `Power.log`.** Формат меняется между билдами игры. Единственный источник правды — реальные логи в `data/fixtures/`. Если в fixtures нет примера нужной конструкции — остановиться и запросить у меня свежий лог, а не угадывать теги.
2. Перед реализацией любого куска парсера — найти соответствующие строки в fixtures и сослаться на них в тесте.
3. Каждая fixture — это `partN.log` + `partN.expected.json` с вручную проверенными контрольными точками. Тесты пишутся от expected-файла.
4. Полезный референс по устоявшимся конструкциям формата — парсеры HearthSim (`hearthstone-deck-tracker`, `python-hearthstone`), но приоритет всегда у фактического содержимого fixtures.

## Правила разработки

- TDD для парсера и советников: сначала тест на fixture, потом код.
- Никаких сетевых запросов в рантайме (кроме опциональной проверки обновлений данных карт по явной команде).
- Каждая фаза завершается работающей демонстрацией: `npm run demo:phaseN` прогоняет fixture и печатает результат.
- Коммиты небольшие, по одному логическому изменению.
- Если задача требует данных, которых нет (лог, ID карты, механика миньона) — спросить, не изобретать.

## Состояние проекта

Обновлять этот раздел при завершении крупных кусков — он единственное, что
переживает смену сессии.

**Фазы 1–5 закрыты и проверены игроком в игре**: оверлей запущен на его
машине (Electron скачал сам игрок), советы идут по живой партии, обратная
связь с семи партий патча 248348 внесена в правила. В среде разработки
GUI не поднять — окно проверяется только игроком, см. docs/live.md.
436 тестов, `npm run typecheck`, `lint`, `test`, `build` зелёные.

Поздним вечером 14.08 игрок принёс **базу знаний JeefHS** (конспект
геймплея топ-игрока) как внешний источник правил. Разбор — в
[docs/jeefhs.md](docs/jeefhs.md): три пункта вошли структурными правилами
(витрина из мусора — довод подняться; ранний реролл не соревнуется
с доступным подъёмом; напоминание о тьюторинге тринкетов за ход
до предложения — после подтверждения игроком), большая часть конспекта
уже покрыта правилами или симулятором, картоспецифика (таблица
активаторов — по словам игрока частично устарела) и спорные места
отложены вопросами к игроку. Disconnect tech и APM-советы отвергнуты
как противоречащие продукту.

Ночью 14.08 подключена **статистика мест** — по предложению игрока
(он прислал ссылки hsreplay; тот закрыт от выгрузки, вместо него — открытые
данные Firestone, та же экосистема, что симулятор и снапшот карт).
`npm run update:bgstats` кладёт снапшот в `data/bgstats/` (сеть только
по явной команде, как у карт); советник получил два применения: **выбор
героя** (канал MULLIGAN теперь в состоянии — `heroChoice`, варианты
ранжируются средним местом, скины приводятся к базовой карте) и **тринкеты**
(среднее место в reason и как разводка при равных своих племенах; голое
«оценить не берёмся» осталось только там, где нет и статистики). Малые
выборки (<500 партий) отфильтрованы. Статистика привязана к патчу —
обновлять вместе со снапшотом карт.

Поздним вечером 14.08 — шестая партия с оверлеем (part14, Сильвана,
5-е место), три пункта: **заклинание-замена** от тринкета («Destroy a
friendly Undead to get a random Undead» — ни статов, ни золота, разбор
возвращал null и совет молчал) распознаётся и целится в наименьшую нежить;
**активации миньонов** («Activate (N): …») советуются — активируемость
тегом `HAS_ACTIVATE_POWER`, цена живым тегом `INTERACTABLE_OBJECT_COST`,
применение блоком PLAY на сущности, стоящей в PLAY, повторно в тот же ход
не советуется; **боевой бонус за племенное ралли** («Rally: Your Undead
have +1 Attack») без своих того племени снят — дул ценность Dustbone
Devastator на борде из элементалей.

Вечером 14.08 закрыты три хвоста с готовой фактурой: **скидка на покупку** читается
с миньона витрины и попадает в цену совета; **состав племён партии**
копится по витрине (`seenShopCardIds` + `lobbyRaces`), фантомные племена
от двуплеменных карт отсеяны, тринкет для невиданного племени говорит
об этом вслух; **тесты состояния part1** нашли и закрыли настоящую дыру —
дамп переподключения не разбирался, и после реконнекта парсер не знал
ни героя, ни тира. Попутно уточнена семантика `finalPlace`: это текущее
место в таблице, финальным оно становится на FINAL_GAMEOVER.

14.08 закрыт «следующий шаг» фазы 5: **расстановка считается против поля** —
когда следующего противника не видели, целью берутся все виденные борды
и средний исход по ним. Советник перестал молчать полпартии (по замеру
16 из 27 точек решения были немыми при виденных бордах). Подробности,
цена и honest-оговорка про гладкий ландшафт — в docs/position.md,
замер — `npm run spike:field`.

Тем же вечером — пятая партия с оверлеем (part13, Хроми, 4-е место):
пять пунктов обратной связи, все закрыты тестами. Бесплатная активная
сила героя советуется (прежде отсекалась условием `cost > 0`), открытие
модального выбора вошло в ключ положения (оверлей показывал «НИЧЕГО»
поверх раскопки), носитель магнита называется и на неполном борде
и выбирается без дубля дара (перерождение на перерождённого — впустую),
заклинание «Destroy a friendly X» целится в жертву, а не «на крупнейшего».

Седьмая партия с оверлеем — part15 (Холли'дэй, **1-е место**, 20:19–20:48
того же 14.08): пять пунктов по пяти скриншотам, все закрыты структурными
правилами с тестами. Пара первого тира больше не держит витрину (порог
тира у второй копии), платная сила «даёт заклинание таверны» советуется
при остатке золота, механика из текста стала синергией (Titus Rivendare
на борде хрипов больше не продаётся), нецелевое заклинание («of each
type») цели не называет, провокация обходит миньонов-«движков»
(Deathstrider). Разбор — в docs/tavern.md, «восьмая порция».

Рабочий цикл, который сложился и работает: игрок играет с оверлеем →
называет неверные советы → его логи становятся фикстурами → правки правил
закрепляются тестами на этих логах. Сырые транскрипты сессий разработки —
в `chat-history/` (не в git).

Три последние итерации цикла — партии 13–14.08 (part9 за Зиреллу, 2-е место,
шесть пунктов; part10 сразу после правок, 6-е место, восемь пунктов;
part11 за Сильвану, 3-е место, семь пунктов — уже без скриншотов, со слов
игрока, моменты найдены в логе по описаниям), все пункты закрыты
и закреплены тестами. По part11: тёмный дар умолкает после трёх зарядов
(счётчик на кнопке), карты-смертники из «Восстания из гробницы» не
советуются в ход получения без хрипа/перерождения, заклинания витрины
видны и покупаются (у них другой CARDTYPE), заморозка ради племени молчит
в ход подъёма, «делать нечего с золотом» превратилось в обновление
от безделья, хвост подъёма стал стадийным. По part9: сила героя с местоимением
в тексте советуется, тринкеты видят племя `MECH`, магнитные мехи не требуют
продажи и называют носителя, модальные выборы (раскопка, тройка, лавка)
разобраны и ранжированы, миньон с племенем в тексте карты держит место
в композиции, несколько розыгрышей складываются в план одной строкой,
советы в оверлее переносятся, а не обрезаются. По part10: заморозка перестала
верить амальгамам и золотым копиям и получила порог от тира, на полном борде
кандидат больше не получает бонусов от собственной жертвы, тройка и вторая
копия покупаются без продажи, заклинания руки (монетка, баффы) видны
и советуются, выбор из заклинаний-сокровищ показан и ранжирован, подъём
называет судьбу остатка золота. Подробности — в [docs/tavern.md](docs/tavern.md),
фактура каналов — в [docs/power-log.md](docs/power-log.md).

### Что в GameState

Фаза, ход, тир, золото (остаток и всего), цена и цель подъёма таверны, предел
тира, герой с силой, свой борд и рука с полными признаками и энчантами,
магазин с признаком заморозки, борд противника, аномалия, счётчики
`globalInfo`, следующий и текущий противник, накопленные борды соперников
с ходом, на котором каждый снят, открытое предложение тринкетов, открытый
модальный выбор (`openChoice`: источник и варианты — раскопка, тройка,
лавка), заклинания руки (`handSpells`: цена и значения плейсхолдеров),
взятые тринкеты всех игроков (dbfId на героях), карты, виденные в витрине
за партию (`seenShopCardIds` — сырьё состава племён), текущее место
в таблице (`finalPlace`, финальное — на конце партии).

### Качество предсказаний

На 35 боях четырёх партий своего патча (`part4`–`part7`, билд 248348):
расхождение калибровки **5.1 п.п.**, Brier **0.035** против 0.25 у «всегда
50%», один пограничный выброс (4.4% при пороге 5%). Передача тринкетов
симулятору улучшила расхождение с 5.8 до 5.1 п.п. Числа перепроверяются
командой `npm run calibrate`, пороги закреплены тестом
`test/advisors/calibration.test.ts`.

**Калибровать можно только на партиях текущего патча.** 13.08 после
обновления карт и симулятора расхождение на партиях билда 246003 выросло
с 3.9 до 9.0 п.п., хотя ни парсер, ни маппер не менялись: поменялась игра,
а записанный исход относится к своему билду. Старые фикстуры остаются
годными для проверки разбора лога — там они и работают.

Проверено против полного перебора 720 расстановок (part3, ход 8), эталон
по 2000 симуляций на вариант: рекомендация занимает **2.4 место из 720**

### Качество советов по таверне

Эвристики покупок сверены с симулятором на 98 ходах ВСЕХ двенадцати партий
текущего патча (`part4`–`part15`, выборка расширена поздним вечером 14.08):
совпадение с лучшим по бою **82%**, средняя цена расхождения **2.60 п.п.**,
на решающих ходах совпадение **67%** при цене промаха **7.6 п.п.**
Перезамер после правил part15 (порог пары, perTextMechMate) регресса
не показал: до правок на десяти партиях было 83% / 2.25 / 67% / 7.3 —
сдвиги в пределах шума расширенной выборки. Перезамер после правил
JeefHS (подъём при мусорной витрине, ранний реролл) — 81% / 2.63 /
64% / 7.7: покупочные очки правки не трогали, ранжирование покупок
прежнее, расхождение — шум несеяного Монте-Карло на почти-ничейных
ходах (цены 0.1–0.3 п.п.). Правки 14.08 — структурные, по диагнозу промахов: боевой
эффект из текста («Rally:», «Summon») и кап щита/вихря/перерождения телом —
разгромные промахи в 50–100 п.п. исчезли, цена ошибок упала вдвое.
Совпадение на решающих по-прежнему скромное — решающий ход и есть тот,
где нужен симулятор; остаток расхождений — экономические карты, которые
ближайший бой честно наказывает (оговорка методики). Случайный выбор дал бы
20–33%. Веса по числам не подгонялись — только структурные правила
с перезамером. Подробности — в [docs/tavern.md](docs/tavern.md).

13.08 правила дважды переработаны по обратной связи игрока: подъём таверны
при отставании ставится выше лучшей покупки (шкалы прежде были несравнимы),
кривая сдвинута на стандартную («тир 2 вторым ходом»), подъём на чётный тир
обещает расширение витрины (замерено: 3/4/4/5/5), появились «разыграть
из руки» и экономическое слагаемое ценности по тексту карты (River Skipper
и родня), заморозка советуется только ради копии под тройку или собираемого
племени — незамороженная витрина обновляется бесплатно.

### Живой режим

Состояние в конце догона — это «сейчас», а не история: обновление приходит
один раз на чтение, после применения всех строк. Правило «на догоне
не советуем» выбрасывало ровно его, и помощник, запущенный посреди партии,
молчал. Закреплено тестом на дописываемом файле.

Живой путь даёт ровно то же состояние, что и пакетный, — это проверяется
тестом на порциях случайного размера, и это единственная защита от их
молчаливого расхождения. Догон файла с начала стоит 234 мс на 41 МБ,
поэтому отдельного быстрого пути не понадобилось. Подробности —
в [docs/live.md](docs/live.md).

**Расстановку в живом режиме почти всегда считать не против кого.** Замер
по всем ходам таверны обеих фикстур: до 13-го хода включительно следующий
противник ни разу не оказался из числа виденных, дальше картинке 7–17 ходов.
Это не дефект реализации — соперников семеро, бой с каждым случается однажды.
Следствие для продукта: советник расстановки в живой игре молчит большую
часть партии, и об этом сказано вслух, а не скрыто.

### Решения, которые НЕ надо переоткрывать

Каждое подтверждено замером или фактурой, ссылки — в `docs/`.

- **Канал-источник — `GameState.DebugPrintPower`.** Приходит раньше
  (20 677 против 131) и именует сущности числовыми id.
- **Неизвестные счётчики `globalInfo` нулями подставлять нельзя.**
  Замерено: калибровка ухудшается вдвое (3.9 → 9.1 п.п.). Отсутствие
  лучше выдуманного нуля.
- **Золотой миньон — тег `PREMIUM`, не суффикс `_G`.** 25 золотых
  в эталонной партии суффикса не имеют.
- **`cards.collectible.json` из ТЗ не годится** — нужен полный набор
  Firestone с `techLevel`, `isBaconPool`, `races`.
- **Снапшот карт надо обновлять с патчем.** Замер 13.08: снапшот от 04.08
  не знал 41 карту из 216 в партии нового билда, почти все — набор BG36.
  Незнакомая карта это не «чуть хуже совет», а совет вслепую.
  Команда `npm run update:cards`.
- **Воспроизводимость симулятора держится на его собственном ГПСЧ, а не
  на подмене `Math.random`.** С версии 1.1.737 пакет захватывает
  `Math.random` в замыкание при загрузке модуля, и поздняя подмена глобали
  на него не действует: три прогона с одним зерном дали 57.0, 58.3 и 52.3%
  побед. Используется пакетный `withRng(createSeededRng(seed), …)`.
- **Фаза 3 выполнима.** Моя ранняя оценка «17 минут на перебор» была
  ошибкой: я принял бюджет ТЗ за факт производительности. Полный перебор
  5040 расстановок — около четырёх минут в поток (замер с прогревом:
  120 мкс на симуляцию плюс 8.5 мс постоянных на вызов), локальный поиск
  укладывается в 3–4 с.
- **Общие случайные числа для сравнения расстановок НЕ работают.** Это было
  предписано ТЗ и моими же заметками, но замер показал 0.9× на близких
  кандидатах, то есть выигрыша нет вовсе: два порядка миньонов расходятся
  по числу бросков с первого размена. Работает другое — накопление симуляций
  у выживших кандидатов. Числа в `docs/position.md`.
- **Опции прогона симулятора надо задавать явно.** Умолчания пакета доигрывают
  бой ради образцов, пересчитывают перцентили каждые 200 симуляций и молча
  обрывают счёт на 8 секундах. Всё выключено в `advisors/battle/simulator.ts`.
- **Значимость считается по величине сравнения, а не по доле побед.** Бывают
  бои, где все расстановки выигрывают в 0% случаев, а решается всё долей
  ничьих; и бывают бои с нулевой дисперсией, где ошибка равна нулю и
  «значимым» становится любой разводящий довесок. Оба случая стоили тихо
  неверного совета и закрыты тестами.
- **Цена подъёма таверны читается из лога, таблицей её не заменить.** Тег
  `COST` кнопки `TB_BaconShopTechUp0N_Button`. Цена падает на единицу за
  каждый ход без подъёма, то есть зависит от всей истории партии.
- **Заморозка соревнуется с бесплатным обновлением, а не с пустотой.**
  Незамороженная витрина обновляется в начале хода даром, поэтому морозить
  можно только то, чего свежая витрина не обещает: копию под тройку или
  собираемое племя. Абсолютный порог ценности это правило уже ломал.
- **Порог «выбор что-то решал» в сверках обязан превышать шум Монте-Карло.**
  Порог 1 п.п. при ошибке разности ~1.6 п.п. давал множество «решающих»
  ходов, состав которого зависел от зерна: 33% совпадений при 800 симуляций
  против 62% при 2000 на одних и тех же партиях.
- **Точка решения в таверне — последнее состояние до первой траты золота.**
  Не первое: витрина наполняется не мгновенно, и снимок заставал в ней одного
  миньона вместо пяти. Не конец фазы: там золото всегда 0 из 10.
- **Применение силы героя и тёмного дара видно только блоком `BlockType=PLAY`
  на их сущностях.** `EXHAUSTED` в фикстурах не встречается ни разу (part8:
  10 нажатий силы — 10 блоков). Сброс «нажато в этом ходу» — по смене `TURN`.
  Недоступность силы — тег `LITERALLY_UNPLAYABLE`; он же блокирует карты
  в руке (замок тринкета), и «разыграть» такие не советуется.
- **Порог реролла обязан расти с тиром.** Плоский порог к пятому тиру
  не срабатывал никогда: миньон там дороже порога одним тиром.
- **Взятые тринкеты читаются с героев, а не из зоны.** Теги
  `BACON_FIRST/SECOND_TRINKET_DATABASE_ID` (значение — dbfId) видны у всех
  восьми игроков. Маркер открытого предложения — `BACON_TRINKET=1`
  в `SETASIDE`; `USE_DISCOVER_VISUALS` не годится, он лишь у части
  вариантов. На выборе все варианты уходят в `REMOVEDFROMGAME`.
- **Цель-поле не трогает поиск: симуляции кандидата делятся между бордами
  поровну, счётчики складываются.** Это послойная выборка среднего по полю;
  накопление, финал и значимость работают на слитых счётчиках как на одном
  борде. Замерено (`npm run spike:field`): постоянная часть вызова множится
  на K (13 → 82 мс на кандидата при K=1 → 7), охват отбора падает до ~30
  кандидатов — и это принято, потому что ландшафт среднего исхода глаже
  одиночного (размах 0–2.5 п.п. против десятков). Следствие заявлено:
  против поля советник чаще честно говорит «менять нечего». Взвешивать
  борды по свежести не стали — данных о том, кто вероятнее выпадет, нет.
- **Сверять покупки против последнего увиденного борда противника нельзя.**
  Он устаревает на 7–17 ходов, все сравнения выходят разгромом 100:0,
  а разброс между кандидатами — тождественный ноль. Для сверки берётся борд,
  который вышел в бою следующего хода на самом деле.
- **Модальные выборы — канал `DebugPrintEntityChoices`/`SendChoices`,
  не зоны.** Раскопка, награда за тройку, лавка аксессуаров — всё приходит
  заголовком с id и строками `Entities[i]` с cardId; закрытие — `SendChoices`
  с тем же id. Id вариантов НЕ совпадают с id зонных копий тех же карт,
  зонный путь тринкетов опаздывает (3 из 4 вариантов в точке решения part9),
  выбор героя идёт тем же каналом с `ChoiceType=MULLIGAN`. Строки каналов
  выбора нельзя пропускать через стек блоков — их отступ чужой. Фактура
  в docs/power-log.md.
- **Ключи племён в таблицах правил — строки `races` снапшота.** Племя
  механизмов называется `MECH`; ключ `MECHANICAL` не совпадал ни с чем,
  и тринкет про мехов при пяти мехах на борде получал «своих таких нет»
  (part9, скриншот). Список рас пула: ALL, BEAST, DEMON, DRAGON, ELEMENTAL,
  MECH, MURLOC, NAGA, PIRATE, QUILBOAR, UNDEAD.
- **Шаблоны «сила даёт миньона» обязаны терпеть местоимение и синонимы.**
  У Зиреллы «Choose a minion in the Tavern. … and add it to your hand» —
  «minion» и глагол в разных предложениях (part9, ход 3). У E.T.C.
  «Discover a Buddy» — слова «minion» нет вовсе (part12). Словарь
  пополняется по фактам таких промахов.
- **Племя тринкета — тег `BACON_SUBSET_<RACE>` на его сущности, текст
  вторичен.** У «Разноцветного компаса» племя в тексте — плейсхолдер `{0}`,
  и текстовый разбор его не видел (part12). Имена тегов совпадают
  со строками `races` снапшота (`MECH`).
- **Цель заклинания-усиления — поле рекомендации, а не слова в reason.**
  Оверлей показывает короткую строку действия, и совет без цели
  перекладывал выбор на игрока (part12).
- **Магнитный мех на полном борде не требует продажи.** `mechanics: MODULAR`
  в снапшоте; совет называет носителя — самый крупный свой мех. Прежний
  совет «разыграть магнита, продав N» отдавал миньона даром (part9, ход 13).
- **Тип карты в снапшоте пишется смешанным регистром** («Minion»,
  «Battleground_trinket») — сравнение без нормализации молча не совпадает
  никогда. Справочник приводит к верхнему регистру.
- **На полном борде ценность кандидата считается против борда БЕЗ жертвы,
  и превосходство обязано превышать `sellMargin`.** Иначе кандидат получает
  бонусы от миньона, которого сам вытесняет: дракончик из руки числил
  бордового дракончика «второй копией» и предлагал продать его же (part10,
  ход 11). Тройка с копией на борде и вторая копия в руку продажи не требуют
  вовсе.
- **Заморозка не верит амальгамам и одноимённым.** «Собираемое племя»
  для заморозки считается без `ALL` и без карт с тем же базовым cardId
  (суффикс `_G` снимается — золотая копия та же карта). Порог заморозки
  растёт с тиром, как у реролла: плоский порог на тире 4 держал витрину
  ради дешёвки второго тира (part10, ходы 3 и 13).
- **Плейсхолдеры `{0}`/`{1}` в текстах снапшота — индексы
  `TAG_SCRIPT_DATA_NUM_1..2` на сущности.** «+{0} Attack» у сокровища —
  это NUM_1=10; у Тавматургии единица улучшения в NUM_2 и растёт по партии.
  Парсить литеральные числа из «{1}» — тихо неверно.
- **Заклинания руки видны только белым списком `CARDTYPE=SPELL`.** Монетка
  таверны создаётся с `COST=1`, живой тег падает до нуля — цену читать
  из тега. Экономическое заклинание советуется, лишь когда его золото
  открывает недоступное действие, иначе честно копится (part10, ходы 5 и 9).
- **У заклинаний ДВА типа: в руке SPELL, в витрине BATTLEGROUND_SPELL.**
  Белый список одного типа молча терял витринные — единственные карты
  магазина с ценой в логе (живой `COST`; part11).
- **Заряды тёмного дара — `TAG_SCRIPT_DATA_NUM_2` на кнопке.** Три на
  партию, 3→2→1→0 по нажатиям; после нуля кнопка остаётся в PLAY с ценой,
  и совет по ней был тихо неверным (part11).
- **Карта из «Восстания из гробницы» помечена энчантом
  `TB_BaconShopBadsongE`** («умрёт, если разыграть в этот ход»). Энчант
  не снимается на следующий ход — ход получения отличает
  `NUM_TURNS_IN_HAND=1`. Розыгрыш свежей советуется только ради хрипа
  или перерождения (part11).
- **В ход подъёма таверны заморозка ради племени молчит.** Свежая витрина
  будет уже нового тира; копия под тройку держит витрину по-прежнему
  (part11, ход 9).
- **Активность силы героя — тег `HAS_ACTIVATE_POWER` на её сущности; цены
  у бесплатной силы нет вовсе (нет тега COST).** Прежнее правило отсекало
  бесплатные условием `cost > 0`, и сила Хроми «Refresh the Tavern» молчала
  всю партию (part13). Советуется только бесплатная И активная сила
  с Refresh-текстом; пассивным «нажать» советовать нельзя.
- **Открытие модального выбора обязано входить в ключ положения.** Раскопка
  открывается, не меняя ни золота, ни бордов, ни руки, — без выбора в ключе
  советник не пересчитывается, и оверлей показывает старые советы поверх
  модального экрана (part13, ход 5). Тот же урок, что с тринкетами в part9.
- **Дар и племена носителя магнита читаются с его карты.** `mechanics`
  минус MODULAR — что дарит (перерождение, щит…); `races` — к кому
  магнитится (рука-протез: к мехам И нежити). Бинарные ключевые слова
  второй раз не дарятся: носитель — крупнейший из тех, у кого дара ещё нет
  (part13, ход 19: перерождение советовалось уже перерождённому). Носитель
  называется и на неполном борде (ход 15). При виденном у соперников яде
  (по накопленным бордам — читаемый факт) носитель со щитом предпочтительнее
  крупного: яд убивает любым касанием, щит его поглощает, магнит со щитом
  в даре снимает угрозу сам. Указано игроком после part13.
- **Заклинание «Destroy a friendly X» целится в жертву, а не «на
  крупнейшего».** Жертва — наименьший свой племени X; без подходящей
  жертвы совет молчит. «Разделка туши» советовалась «на» голема 200/122 —
  уничтожить главную карту борда, к тому же не-нежить (part13, ход 21).
- **Статистика мест — открытые данные Firestone, не hsreplay.** hsreplay
  закрыт от выгрузки (403); Firestone публикует средние места героев
  и тринкетов открытыми JSON (`static.zerotoheroes.com/api/bgs/…`,
  срез last-patch / mmr-100), идентификаторы карт совпадают с нашими.
  Это ЧУЖИЕ агрегированные данные: в советах они всегда подписаны
  «по статистике», малые выборки (<500 партий) отфильтрованы, снапшот
  живёт в `data/bgstats/` и устаревает с патчем. Своих правил ценности
  героев нет и не выдумывается — статистика и есть их свёртка.
- **Выбор героя — тот же канал выборов с `ChoiceType=MULLIGAN`, отдельным
  полем `heroChoice`.** Сущность героя-заготовки при этом уже существует
  (part14) — экран выбора включается по самому выбору, не по отсутствию
  героя. Среди вариантов бывают скины (`_SKIN_A`) — статистика приводится
  к базовой карте.
- **Активация миньона — тег `HAS_ACTIVATE_POWER`, цена — живой тег
  `INTERACTABLE_OBJECT_COST` на нём же.** Цена сходится с плейсхолдером
  «Activate ({N})» → `TAG_SCRIPT_DATA_NUM`. Применение — блок PLAY
  на сущности, СТОЯЩЕЙ в PLAY: розыгрыш из руки отличается зоной (part14,
  Suspicious Prisonguard). Снимается ли доступность тегом после нажатия,
  в фикстурах не видно — «нажато в этом ходу» считается блоками, как
  у силы героя.
- **Заклинание-замена («Destroy a friendly X to get a random X») — свой
  распознанный эффект.** В тексте ни статов, ни золота, и разбор «только
  статы/золото/щит» возвращал null — заклинание наклейки Тюремщика молчало
  всю партию (part14). Цель — наименьший свой подходящего племени.
- **Боевой эффект «вашим \<племени\>» пуст без своих того племени.**
  «Rally: Your Undead have +1 Attack» на борде элементалей не делает
  ничего, а бонус дул ценность (part14, ход 21, Dustbone Devastator).
  Призывов это не касается: «Summon a Beast» приносит тело независимо
  от борда.
- **Скидка на покупку — тег `BACON_REDUCE_BUY_COST` на самом миньоне
  витрины.** part3: 9999 — миньоны даром (кламп в ноль), part4: 2 — цена 1
  у части витрины при трёх у остальных. Цена совета и «по карману ли»
  считаются через `buyCostOf` по каждому миньону отдельно.
- **Состав племён партии — по однoплеменным миньонам витрины, не по
  `CARDRACE`.** Строковый `CARDRACE` показывает одно племя даже
  у двуплеменной карты и создаёт фантомы: MECHANICAL и DRAGON в part11 —
  от «Руки-протеза» (MECH/UNDEAD) и Firescale Hoarder (DRAGON/NAGA),
  партий без мехов и драконов. Витрина предлагает только пул, поэтому
  однoплеменный миньон в ней доказывает племя; двуплеменные и амальгамы —
  нет. `seenShopCardIds` копится в step, а не в snapshot: живой и пакетный
  пути обязаны давать одно состояние.
- **Пара под тройку морозится только картой не ниже тира таверны.** Вторая
  копия — ставка на будущую тройку, а не тройка, и бонус копии сам же
  пробивал порог ценности: заморозка Buzzing Vermin 1/1 первого тира при
  таверне 2 (part15, ход 5). Третья копия собирает тройку немедленно
  и от тира не зависит.
- **Платная сила «даёт заклинание таверны» советуется как экономика.**
  «Get a random Tavern spell» за 1 (Холли'дэй, part15): ценность —
  примерно цена заклинания в витрине (два золота по курсу), очки за вычетом
  цены силы; сила за 2+ честно молчит. При остатке в 1 золото совет молчал,
  и золото сгорало.
- **Механика, названная словами в тексте, — синергия** (`perTextMechMate`,
  таблица `mechanicTextWords`: DEATHRATTLE, BACON_RALLY). Titus Rivendare
  («Your Deathrattles trigger an extra time», AURA, без племени) на борде
  хрипов был слабейшим по статам и предлагался в продажу (part15, ход 17).
  Собственная механика синергией не считается («Deathrattle:» о себе).
  «Taunt» словами не разбирается: в текстах он описывает призываемых.
- **У заклинания без выбора цели цель не называется.** «Give a friendly
  minion of each type +2/+2» (Misplaced Tea Set, part15) раздаёт сама,
  а совет писал «→ на Deathstrider». Шаблоны `untargetedSpellWords`:
  of each type, random, left-/right-most, all friendly, your minions.
- **Провокация не вешается на миньона-«движка»** (AURA или текст-триггер
  «After/Whenever/At the start…», `engineTextWords`): она зовёт удары,
  а ценность движка — эффект. Slimy Shield советовался на Deathstrider —
  игрок не хочет его в приоритете ударов (part15, ход 19). Цель —
  крупнейший из остальных; борд целиком из движков возвращает крупнейшего.
- **Мусорная витрина — довод подняться, а не покупать и не крутить.**
  Правило из базы знаний JeefHS (docs/jeefhs.md), внесено по указанию
  игрока: когда лучший кандидат ниже порога «покупать нечего» (тот же
  порог, что у реролла), подъём получает очки выше слабых покупок —
  прежде подъём «по графику» имел ноль очков и проигрывал любому телу.
  Туда же: до `lateRerollTier` реролл молчит, пока подъём доступен
  и по карману; при недоступном подъёме (здоровье, тир, золото) реролл
  живёт — «золото иначе сгорит».
- **Предложения тринкетов открываются на ходах 11 и 17** (наша нумерация;
  6-й и 9-й ходы таверны) — замерено по всем двенадцати партиям билда
  248348, ходы в `rules.trinketOfferTurns`. Игра подбирает предложение
  под борд (тьюторинг, подтверждён игроком по базе JeefHS) — за ход
  до предложения советник напоминает держать 2+ миньонов желаемого
  племени (`trinketForecast`); амальгамы сигналом не считаются.
- **Дамп переподключения — блоки `GameEntity/Player EntityID=…` со
  строками-продолжениями `tag=`.** `HERO_ENTITY` там приходит НЕ как
  TAG_CHANGE, а тегом блока Player; разбор без этой ветки оставлял партию
  после реконнекта без героя и с тиром 1 (part1, сегменты 2–4).
  `PLAYER_LEADERBOARD_PLACE` живёт всю партию как текущее место —
  финальным становится только на FINAL_GAMEOVER.

### Отложено сознательно, с причинами

- **Статистика мест для тёмных даров, миньонов и композиций.** У Firestone
  есть и card-stats, и comp-stats, и quest-stats — подключены только герои
  и тринкеты: там статистика отвечает на прямое «оценить не берёмся».
  Вливать глобальные винрейты миньонов в ценность покупки — значит
  смешать наш контекстный расчёт с бесконтекстным средним; не делается
  без отдельного замера сверкой.
- **Активации со сложными эффектами.** Простые активации советуются
  (см. «не переоткрывать»): бафф-статы и «получить миньона». Кражи,
  поглощения, консервация статов («Living Prison») — эффекты без прямой
  цены в статах, совет их честно не оценивает.
- **Силы героя вне «даёт миньона», «бесплатно обновляет витрину» и «даёт
  заклинание таверны»** — урон, баффы, прочая экономика: совет не берётся
  судить, как и с тринкетами. Советуются сила, дающая миньона, бесплатная
  активная сила-обновление и платная сила-заклинание дешевле своей ценности
  (см. «не переоткрывать»).
- **Экономические эффекты тринкетов.** Взятые тринкеты передаются
  симулятору (замер: калибровка 5.8 → 5.1 п.п.), выбор советуется
  по племенам из текста карты. Но тринкеты, меняющие экономику (цену
  покупки, обновления), в советнике таверны не учитываются.
- **`validTribes`.** Теги `BACON_SUBSET_*` висят на миньонах, а не на
  `GameEntity`, то есть означают принадлежность карты к племени, а не
  состав партии. На ТРИНКЕТАХ тот же тег называет племя эффекта — это
  используется в советах (part12), но состава партии по-прежнему не даёт.
- **`NaN` у статов спавнов.** Виден в логе симулятора вместе с
  «short-circuiting simulation». На него приходится единственный выброс
  калибровки. Нулями не лечится (см. выше).
- **Восемь воркеров вместо одного.** Один поднят в фазе 5 и снял главную боль:
  счёт не держит интерфейс. Восьмикратный запас потребует по снапшоту карт
  на воркер и своей схемы разбиения поиска — работа отдельная и пока
  не нужная.
- **Расстановка противника не перебирается.** Он тоже её выбирает; мы играем
  против того порядка, который видели в последнем бою с ним. Возраст этой
  картинки лежит в `staleTurns`.
- **Базовая цена покупки миньона — правило игры, не факт лога**: тега `COST`
  у миньонов витрины нет, тройка золотых лежит в `rules.ts`. Скидки при этом
  читаются (`BACON_REDUCE_BUY_COST`, см. «не переоткрывать») — неразобранной
  осталась только гипотетическая НАЦЕНКА: случаев дороже трёх в фикстурах
  не встречалось.
- **Ключевые пары карт в эвристиках таверны.** ТЗ их упоминает; синергия
  сейчас считается по племени, копиям и племени, названному в тексте карты
  (`perTextTribeMate`, part9). Таблица пар — это данные, которых у нас нет,
  а выдумывать их значит вписать в правила чьё-то мнение под видом факта.
  Не разобран честный частный случай: текст, называющий конкретную КАРТУ
  (Automaton Portrait призывает Ancestral Automaton) — правила видят только
  племена.
- **Сравнение «телом против примагнитить» не делается.** Носитель теперь
  выбирается без дубля дара и называется всегда (part13), но что выгоднее
  на неполном борде — тело в слот или статы носителю — правила не судят:
  цены слота у них нет.
- **План розыгрыша продаёт не больше одного миньона.** Жертва считается
  против исходного борда; второй шаг через продажу продавал бы того же.
- **Цель баффа — «крупнейший свой», как у магнита.** Кому полезнее +1/+1
  или щит, правила не судят. Два исключения по фактам part15: бафф
  с провокацией обходит движков, нецелевое заклинание цели не называет
  (см. «не переоткрывать»).
- **Заклинания вне «золото» и «статы» не оцениваются.** Скидки («Отправные
  цены»), бананы в руку, раскопки-заклинания — эффекты без прямой цены;
  в совете по выбору они честно помечены «оценить не берёмся».
- **Полный оптимизатор трат хода не строится.** Судьба остатка золота
  называется словами (стадийно: рано «сгорит — цена подъёма», поздно
  «на обновление»), но корзина «подъём + реролл против двух покупок»
  целиком не перебирается — отдельная задача со своим замером.
- **Состав племён в советах используется точечно.** Читается он теперь
  честно (см. «не переоткрывать»), но фильтрует пока только одно: тринкет
  для племени, невиданного в витринах партии, говорит об этом вслух.
  Остальные советы состав не сверяют — свои миньоны племени обычно
  доказывают его сами, а фантом возможен лишь от карт, полученных
  вне магазина.
- **Choose One в текстах заклинаний считается с завышением** — суммируются
  обе ветви «+{0}/+{1}; or +{2}/+{3}», выбирается одна.

### Следующий шаг

Седьмая партия (part15) выиграна, и жалоб на правки прошлых итераций
не было — все пять пунктов оказались про непокрытые места: пара под тройку,
платная сила-экономика, усилители механик, нецелевые заклинания, цель
провокации. Все закрыты структурными правилами с перезамером. Дальше —
продолжать цикл: следующая партия проверит сегодняшние пять правок.
Открытый вопрос к игроку прежний: не мешают ли частые честные «менять
нечего» от цели-поля.

На вопрос игрока «выгрузить ли из hsreplay, что делают герои и карты»
отвечено: данные о том, что делает карта, уже есть — снапшот Firestone
несёт текст, механики и племена каждой карты, и все пять промахов part15
были не от нехватки данных, а от правил, которые эти поля не читали
(текст Titus лежал в снапшоте, «of each type» у сервиза — тоже).
Статистика мест уже берётся снапшотом Firestone (`npm run update:bgstats`,
герои и тринкеты); у hsreplay открытого API нет, и новых данных он бы
не добавил.

По базе знаний JeefHS (docs/jeefhs.md) игрок ответил: тьюторинг
тринкетов подтверждён (напоминание внесено), таблица активаторов
частично устарела (ждём список актуальных карт от игрока — вслепую
не вносится), порог подъёма по здоровью жалоб не вызывал (не трогаем).
Открытым остался один вопрос: давать ли статистике мест перевешивать
слабую племенную синергию в ранжировании тринкетов — переформулирован
игроку понятнее.

Что ещё осталось незакрытым:

- **совпадение эвристик таверны с симулятором на решающих ходах — 67%**
  (замер `npm run validate:tavern`, docs/tavern.md). 14.08 цена промахов
  снижена вдвое структурными правками, но сам процент упирается в предел
  эвристики: решающий ход — тот, где нужен симулятор. Следующий уровень —
  досчитывать решающие покупки симулятором в живом воркере, это отдельная
  задача;
- **окно оверлея в среде разработки не запускалось** — бинарник Electron
  не скачался. У игрока работает; вид покрыт тестами;
- **фаза 6, ML** — по ТЗ отдельное задание, начинать после накопления
  датасета собственных партий.

## Настройка логирования — обязательна, иначе данных не будет

Два файла в **разных** местах, это легко перепутать:

**`%LOCALAPPDATA%\Blizzard\Hearthstone\log.config`** — что логировать:

```ini
[Power]
FilePrinting=true
Verbose=true
```

**`<каталог установки игры>\client.config`** — предел размера лога:

```ini
[Log]
FileSizeLimit.Int=1000000
```

Без второго клиент обрывает **всё** файловое логирование на 10 000 КБ и больше
не возобновляет: полная партия BG весит ~40 МБ и не влезает. Настройка читается
один раз при старте клиента. Файл лежит рядом с игрой, поэтому обновление
Hearthstone может его снести — `ensureLogSizeLimit` проверяет и чинит.

## Что известно про формат Power.log

**Полная фактура — в [docs/power-log.md](docs/power-log.md).** Там всё с
доказательствами из фикстур: числа, цитаты строк, что проверено человеком,
что скриншотом, а что остаётся гипотезой. При работе с парсером читать оттуда,
а не вспоминать.

Ниже только то, на чём ломаются чаще всего. Каждый пункт стоил отдельного бага,
и все они дают **не падение, а тихо неверный результат**:

1. **UTF-8 без BOM, переводы строк смешанные.** Обычные строки CRLF, баннер
   обрезки — одиночные LF. Разбивать по `/\r?\n/`.
2. **`entityName` может содержать вложенные скобки** —
   `[entityName=UNKNOWN ENTITY [cardType=INVALID] id=255 …]`, около 10% всех
   дескрипторов. Разбирать позиционно по именам полей, не по закрывающей скобке.
3. **Канал-источник — `GameState.DebugPrintPower`.** `PowerTaskList` дублирует
   его событие в событие; применять оба — применить теги дважды.
4. **`BLOCK_END` есть не у каждого `BLOCK_START`.** Вложенность считать
   по отступу, а не по парности.
5. **Дескриптор в `TAG_CHANGE` показывает состояние ДО изменения.** Зону
   и позицию брать только из явных тегов, иначе мёртвые миньоны воскресают.
6. **`HIDE_ENTITY` несёт смену зоны и начинается не с `TAG_CHANGE`.**
   Там же: **`SHOW_ENTITY` называет сущность через `Entity=`, а `FULL_ENTITY`
   через `ID=`** — разбор, знающий одну форму, теряет 1349 раскрытий карт
   за партию и оставляет их без `cardId`.
7. **Отбирать сущности белым списком** (`CARDTYPE=MINION`), а не «всё кроме».
8. **Одинаковые теги приходят на разные сущности с разным смыслом.** `TURN`
   на `GameEntity` — ход партии, на игроке — его счётчик, вдвое меньше.
9. **Своего игрока определять по ненулевому `GameAccountId`**, не по номеру:
   `PlayerID` меняется между партиями (в фикстурах 4 и 3 у одного человека).
10. **Золото — это `RESOURCES` минус `RESOURCES_USED`.** Прямого тега
    на остаток нет.
11. **Следующий противник известен заранее** — тег `NEXT_OPPONENT_PLAYER_ID`
    в таверне, проверено 18 совпадений из 18. Кто именно скрыт за чужим слотом,
    определяется через тег `PLAYER_ID` его героя, а не по подписи слота:
    та в поздних боях остаётся «Бармен Боб». Тег
    `BACON_CURRENT_COMBAT_PLAYER_ID` — это НЕ противник, а сам игрок.
12. **Борд противника снимать в начале боя**, по первому блоку `ATTACK`:
    к выходу в таверну его миньоны уже убраны из `PLAY`.

## Как размечать новые фикстуры

Видео бесполезно — ассистент его не читает. Работает так:

1. Игрок делает 4–6 **скриншотов** в конце фазы таверны, на разных ходах.
2. Кладёт в `data/screenshots/` (в git не коммитятся, см. `.gitignore`).
3. Ассистент прогоняет `npm run demo:phase1` на логе и сверяет сам.
4. Совпавшее идёт в `partN.expected.json` с пометкой `verifiedBy: скриншот`.

Скриншоты снимаются в середине фазы, а демо печатает её конец — расхождение
в единицу здоровья это норма, а не баг. Проверять то, что от момента не зависит:
состав, порядок, атаку, золото, тир.

Пометки в `expected.json` различаются по силе: `подтверждено человеком` —
игрок видел это своими глазами в игре; `скриншот` — сверено по картинке.
